The mental model shift

Every framework war aside, React asks you to think about UI in one specific way. Get this one idea right and almost everything else below is just vocabulary for it.

Old model: steps

"Find the button. Add a click listener. When clicked, find the counter element. Read its text. Add one. Write it back." You describe how to change the page, one instruction at a time.

React model: description

"The counter's text is always count." You describe what the UI looks like for any given data — React figures out which instructions to run to get there.

The one sentence that explains 90% of React

UI = a function of state. Change the state, call the function again (React does this for you), get new UI. You almost never touch the DOM yourself — you just describe what it should look like right now.

JSX fundamentals

Before components make sense, JSX itself needs to stop looking strange. It compiles down to plain JavaScript function calls — every rule below exists because of that one fact.

JSX is JavaScript wearing HTML's clothes

<h1>Hello</h1> isn't a string and isn't real HTML — Babel compiles it into React.createElement("h1", null, "Hello"). Everything below follows from that: since it's really a function call, it has to obey JavaScript's rules, not HTML's.

Curly braces drop into JavaScript

Anywhere inside JSX, { } means "stop reading this as markup, evaluate this as a JS expression." Only expressions — no if statements or for loops directly inside braces, only things that produce a value.

Click Run

className, not class — style is an object

class is a reserved JavaScript keyword, so JSX uses className instead. And since style takes a JS expression, it's a plain object — {{ }} is just an object literal { } sitting inside the expression braces { }, not special syntax.

One root element — or a Fragment

A component can only return one element, because it compiles to one function call. To return sibling elements without adding an extra wrapper <div> to the actual page, wrap them in <>...</> — a Fragment, which renders nothing itself.

Quick reference — the four rules above

1) JSX compiles to React.createElement calls. 2) { } holds any JS expression. 3) className not class; style is an object. 4) One root element per return, or use <></>. Everything else about JSX follows from these.

Components & props

A component is just a function that returns JSX. Props are the arguments you pass it — read-only, flowing one direction: parent to child.

jsx
Click Run
The rule that matters

Props flow down, never up. A child never reaches into its parent and changes something. If a child needs to affect its parent, the parent passes it a function to call — see "lifting state up" below.

One more idiom you'll see in almost every component: { label } in the function signature is just destructuring — it pulls props.label out directly instead of writing props.label everywhere in the body. You can also give a prop a default value with =, exactly like a normal function parameter.

State — useState

State is data a component remembers between renders. Calling the setter doesn't just store a new value — it tells React "re-render this component now."

Click Run
Each component's state is private

Two <Toggle /> instances on the same page each get their own independent isOn — state belongs to the component instance, not the function definition.

There are two ways to update state: setValue(value + 1) uses the value from the current render, while setValue(v => v + 1) — a functional update — always gets the freshest value, even if several updates happen before React re-renders. When the new value depends on the old one, prefer the function form.

Events & controlled inputs

In React, form inputs usually have their value driven by state, not by the browser's own internal input state — that's what "controlled" means.

jsx
Click Run
Why "controlled"

The input's value is always exactly whatever name is. React — not the DOM — is the single source of truth. This is what makes validation, formatting, and "clear this field" trivial: you just change state.

Because the input is controlled, live validation is just an ordinary variable computed from state during render — no separate "validate on submit" step required, and the feedback updates on every keystroke for free.

Lifting state up

Two sibling components can't talk to each other directly. The fix is always the same: move the shared state to their common parent, then pass it down as props.

jsx
Click Run
How to know where state belongs

Find the closest common ancestor of every component that needs the value. That's where the state lives. Everything below just receives it as a prop — either the value itself, or a function to change it.

useEffect, used correctly

An effect synchronizes your component with something outside React — a timer, a subscription, a manual DOM API, a fetch call. It is not a general "run this when something changes" hook.

The dependency array is not optional decoration

[] means "run once." [count] means "re-run whenever count changes." Leaving it off entirely means "run after every single render" — almost never what you actually want, and a common source of infinite loops when the effect itself updates state it depends on.

Thinking in React

A methodology for turning any design or feature request into components, before you write a single line of state logic. This is the process, not just the patterns.

1. Break the UI into components

Draw boxes around every piece of the design. Each box that represents one thing (one row, one card, one panel) is a candidate component.

2. Build a static version first

Render the whole tree using only props, top-down, with zero state and zero interactivity. This forces you to get the component hierarchy right before anything can move.

3. Find the minimal state

Ask of every piece of data: does it change over time? Can it be computed from other state or props? If yes to the second question, it's not state — it's derived, and it doesn't belong in useState at all.

4. Decide where each piece of state lives

Find every component that needs to read or change it. State lives in their closest common parent — exactly the "lifting state up" pattern from earlier, arrived at deliberately instead of by trial and error.

All four steps, in one component tree

A searchable product list. The component boundaries came from step 1 (a search box, a table, a row). The state — just searchTerm — came from step 3: filteredProducts is derived from it, not separate state. And searchTerm lives in App because both SearchBox and ProductTable need it — step 4.

The step people skip

Step 2 — the static version — feels slow when you're excited to make something interactive. Skipping it is exactly how you end up with state in the wrong place and a component tree you have to rebuild halfway through. Five extra minutes here saves an hour later.

Zero → professional, in order

Do these in sequence, not in parallel. Each one only needs what came before it. Click to mark done as you go.

1

Static component tree

Build a page of nested components using only props — zero state, zero events. Get comfortable with JSX and composition first.

2

One component, one piece of state

A counter, a toggle, a like button. Nothing shared, nothing lifted — just you and useState.

3

A controlled form with validation

Multiple inputs, all driven by state, with inline feedback. This is where events and state combine for real.

4

A list with add, remove, and edit

Practice .map(), stable keys, and updating arrays immutably under real pressure.

5

Two siblings sharing state

Force yourself to lift state to a common parent instead of reaching for a library.

6

Extract your first custom hook

Find logic you've written twice. Pull it into a useSomething function.

7

Fetch real data

Loading state, error state, success state — a real useEffect synchronizing with an external API.

8

Compose it all into one small app

A todo app, a mini dashboard, anything with multiple connected pieces. This is the first thing that will actually feel like "a React app."

After these eight

You're not "done learning React" — nobody is. But you now have every pattern you'll use in 99% of real components. Everything past this point (routing, global state libraries, performance tuning) is a tool you reach for when a specific problem actually shows up, not something to learn preemptively.

Habits that separate professionals

Not talent. Repetition, applied to the right things. Click each one you're committing to.

Before reaching for useEffect, ask "am I just computing a value?" — if so, compute it during render instead
Never mutate state directly — always create a new array or object and call the setter
Read the actual error in the console before guessing — React's error messages usually name the exact problem
Keep state as close to where it's used as possible — lift it up only when something else genuinely needs it
Use stable, unique keys on lists — never the array index once the list can reorder
Reach for composition (children, props) before reaching for a state-management library
Extract a custom hook the second you copy-paste stateful logic into a second component
