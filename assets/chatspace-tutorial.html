Building ChatSpace — a live chat app, entirely inside Django

Django Channels extends Django's own request-handling to speak WebSocket — same models, views, templates, and ORM you already know. The one new problem: a chat message has to reach every other open browser tab in the room, not just the sender. Regular request/response can't do that. Channels can.

  • Named chat rooms, created via the admin
  • Room page with history + a live, no-refresh message stream
  • Any logged-in user can post to any room
  • Messages persist to the database — history survives a refresh
one process, two lanes — traced fully in Step 16

Why channels is installed up front

Unlike a Django app you bolt on later, Channels isn't a feature you add to a finished project — it changes how the whole project is served (ASGI instead of plain WSGI). That decision has to be made before startproject even runs, not discovered mid-build.

Why ASGI_APPLICATION matters immediately

Even though asgi.py isn't rewritten until Step 16, this setting tells Django (and manage.py runserver, once Channels is installed) which ASGI callable to boot. Without it, Channels has no idea where to find the routing defined later.

Why InMemoryChannelLayer, not Redis

A "channel layer" is how one WebSocket connection tells another "a new message arrived" — it needs shared, cross-connection state. In production that has to be Redis (channels_redis), because a real deployment runs multiple server processes that don't share memory. For a single runserver process on your own machine, InMemoryChannelLayer does the same job with zero extra infrastructure — perfect for learning the pattern, not for production traffic.

Step 4 — Open chat/models.py

chat/models.py
from django.db import models
from django.contrib.auth.models import User

class Room(models.Model):
    name = models.CharField(max_length=100)
    slug = models.SlugField(unique=True)

    def __str__(self):
        return self.name


class Message(models.Model):
    room = models.ForeignKey(Room, related_name='messages', on_delete=models.CASCADE)
    author = models.ForeignKey(User, on_delete=models.CASCADE)
    content = models.CharField(max_length=500)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ['created_at']

    def __str__(self):
        return f"{self.author}: {self.content[:30]}"
Why messages are a plain Django model, even in a "real-time" app

The WebSocket layer (Step 14) only handles delivery — getting a message to open tabs instantly. Storage is a completely separate concern and doesn't care whether the message arrived over HTTP or a socket. Keeping this model exactly like any other Django model is what lets Step 13's room page show message history using an ordinary queryset — no different from a product list.

Step 8 — Open chat/views.py

chat/views.py
from django.shortcuts import render, get_object_or_404
from django.contrib.auth.decorators import login_required
from .models import Room

@login_required
def room_list(request):
    rooms = Room.objects.all()
    return render(request, 'chat/room_list.html', {'rooms': rooms})

@login_required
def room(request, slug):
    room = get_object_or_404(Room, slug=slug)
    messages = room.messages.select_related('author')
    return render(request, 'chat/room.html', {'room': room, 'messages': messages})

This view's only job is rendering the page shell and message history — the live part comes entirely from the WebSocket built in Steps 14–17, not from this view. That split — HTTP view loads the page and past messages, WebSocket handles everything after this point in time — is the core idea of the whole project.

Why select_related('author')

It avoids an N+1 query while looping over message history in the template — the same efficiency principle applied here from the start.

Why json_script, not {{ room.slug }} straight into JS

{{ room.slug|json_script:"room-slug" }} is the one new tag in this project — it safely embeds the room's slug as JSON inside a <script type="application/json"> tag, so Step 17's JavaScript can read it without any risk of the slug breaking out of a quoted string.

The #message-log, #message-input, #message-submit IDs are written now, deliberately — Step 17's JavaScript will target these exact IDs, the same "write the interface first" habit every project in this series has followed.

Terminal check: python manage.py runserver — log in, visit the room list, open "General." You should see the (currently empty) message log and an input box that does nothing yet. Everything up to here is plain Django; nothing real-time exists until the next steps.
WS LANE

Step 14 — Create chat/consumers.py (new file)

This is the Channels equivalent of views.py — instead of handling one request and returning one response, a consumer handles one open WebSocket connection for as long as it stays open, and can send messages back at any time, not just in reply to something the client sent.

chat/consumers.py
import json
from channels.generic.websocket import AsyncWebsocketConsumer
from channels.db import database_sync_to_async
from .models import Room, Message

class ChatConsumer(AsyncWebsocketConsumer):
    async def connect(self):
        self.room_slug = self.scope['url_route']['kwargs']['slug']
        self.room_group_name = f'chat_{self.room_slug}'

        await self.channel_layer.group_add(self.room_group_name, self.channel_name)
        await self.accept()

    async def disconnect(self, close_code):
        await self.channel_layer.group_discard(self.room_group_name, self.channel_name)

    async def receive(self, text_data):
        data = json.loads(text_data)
        content = data['message'].strip()
        if not content:
            return

        user = self.scope['user']
        await self.save_message(user, content)

        await self.channel_layer.group_send(
            self.room_group_name,
            {
                'type': 'chat_message',
                'username': user.username,
                'message': content,
            }
        )

    async def chat_message(self, event):
        await self.send(text_data=json.dumps({
            'username': event['username'],
            'message': event['message'],
        }))

    @database_sync_to_async
    def save_message(self, user, content):
        room = Room.objects.get(slug=self.room_slug)
        Message.objects.create(room=room, author=user, content=content)

Reading each method in the order events actually happen:

connect()

Runs once, when a browser opens the socket. self.scope['url_route']['kwargs']['slug'] reads the room slug out of the URL (wired in Step 15) — the same job slug does in a normal Django view's URL kwargs. group_add joins a named "group" — every consumer in chat_General, for instance, can now receive anything sent to that group. That's the fan-out mechanism a plain HTTP view has no equivalent for.

receive()

Runs every time this specific browser sends a message over the socket. It saves the message to the database, then calls group_send — which doesn't send anything directly to this browser, it broadcasts to the whole group (everyone in the same room, including the sender).

chat_message()

This method's name isn't arbitrary: group_send's 'type': 'chat_message' tells Channels to call this exact method on every consumer in the group. It runs once per connected browser, and is what actually pushes the JSON out over each individual socket via self.send().

save_message()

Wrapped in @database_sync_to_async because Django's ORM is synchronous (blocking) code, but a consumer's methods are async. This decorator runs the wrapped function safely on a separate thread pool instead of blocking the entire async event loop — every database call inside a consumer needs this wrapper, no exceptions.

Why self.scope['user'], not something the client sends

The message's content comes from the browser, but the user never does — trusting a client-supplied username would let anyone impersonate anyone else. scope['user'] is populated by Channels' auth middleware (wired in Step 16) from the same session cookie a normal Django view would use, so it's exactly as trustworthy as request.user anywhere else.

WS LANE

Step 15 — Create chat/routing.py (new file)

A consumer needs a URL pattern too — just a different kind, since it's matched against a WebSocket connection, not an HTTP request.

chat/routing.py
from django.urls import re_path
from . import consumers

websocket_urlpatterns = [
    re_path(r'ws/chat/(?P<slug>[\w-]+)/$', consumers.ChatConsumer.as_asgi()),
]

re_path (regex-based) is used here instead of path() — Channels' routing predates path()'s cleaner syntax, and this is still the conventional way most Channels tutorials and the official docs express WebSocket routes. [\w-]+ matches the same kind of slug a SlugField produces.

WS LANE

Step 16 — Open chat_project/asgi.py

This is the file every earlier project in this series generated and never touched. Now it earns its purpose: routing HTTP requests one way and WebSocket connections another, out of the same running server process.

Replace the file's contents with:

chat_project/asgi.py
import os
from django.core.asgi import get_asgi_application
os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'chat_project.settings')
django_asgi_app = get_asgi_application()

from channels.routing import ProtocolTypeRouter, URLRouter
from channels.auth import AuthMiddlewareStack
import chat.routing

application = ProtocolTypeRouter({
    'http': django_asgi_app,
    'websocket': AuthMiddlewareStack(
        URLRouter(chat.routing.websocket_urlpatterns)
    ),
})
Why django_asgi_app is created before importing chat.routing

Django's app registry has to finish initializing before any code that imports models (like chat/consumers.py, via chat/routing.py) is allowed to run — importing chat.routing too early raises AppRegistryNotReady. This exact ordering is one of the most common Channels setup mistakes.

Tracing what this router actually does:

Incoming connection │ ▼ ProtocolTypeRouter checks the connection type │ ├── 'http' → django_asgi_app → the entire normal Django stack │ (urls.py → views.py → templates — everything from Steps 8–13) │ └── 'websocket' → AuthMiddlewareStack (reads the session cookie, populates scope['user']) → URLRouter(chat.routing.websocket_urlpatterns) → matches ws/chat/<slug>/ → ChatConsumer

AuthMiddlewareStack is what makes self.scope['user'] in consumers.py (Step 14) trustworthy — without it, every WebSocket connection would see an AnonymousUser, regardless of whether the browser is logged in on the HTTP side.

WS LANE

Step 17 — Open room.html once more — add the WebSocket client

Everything server-side is now in place. This is the last piece: the browser code that opens the socket, sends what's typed, and renders what comes back.

Add at the bottom of room.html:

chat/templates/chat/room.html
{% block extra_js %}
<script>
    const roomSlug = JSON.parse(document.getElementById('room-slug').textContent);
    const socket = new WebSocket(
        (window.location.protocol === 'https:' ? 'wss://' : 'ws://')
        + window.location.host
        + '/ws/chat/' + roomSlug + '/'
    );

    const log = document.getElementById('message-log');
    const input = document.getElementById('message-input');
    const submit = document.getElementById('message-submit');

    socket.onmessage = function (event) {
        const data = JSON.parse(event.data);
        const p = document.createElement('p');
        p.setAttribute('data-message', '');
        p.innerHTML = `<strong>${data.username}:</strong> ${data.message}`;
        log.appendChild(p);
        log.scrollTop = log.scrollHeight;
    };

    socket.onclose = function () {
        console.error('Chat socket closed unexpectedly — refresh to reconnect.');
    };

    function sendMessage() {
        const text = input.value.trim();
        if (!text) return;
        socket.send(JSON.stringify({ message: text }));
        input.value = '';
    }

    submit.addEventListener('click', sendMessage);
    input.addEventListener('keydown', function (e) {
        if (e.key === 'Enter') sendMessage();
    });
</script>
{% endblock %}
Why roomSlug is read from json_script, not typed directly into this script

The slug is server-controlled data ({{ room.slug }}) being placed into JavaScript — exactly the situation Django's own docs warn needs care. json_script guarantees it arrives as safely-escaped JSON, so JSON.parse(...) is always parsing valid, safe data no matter what characters end up in a room's slug.

Why the socket URL is built from window.location, not hardcoded

Hardcoding ws://127.0.0.1:8000/... would break the moment this is deployed anywhere other than local development — a different host, and https pages require wss, not ws. Building it from the current page's own location keeps it correct everywhere automatically.

Why the sender's message isn't appended inside sendMessage()

The sender's own message only appears once it comes back through socket.onmessage — because group_send (Step 14) broadcasts to everyone in the group, including the sender. This is deliberate: the message the sender sees is the exact same one everyone else sees, confirmed as actually saved and broadcast, not just optimistically drawn on screen before we know it worked.

VERIFY

Step 19 — Terminal-free: test the full flow in two tabs

  1. Log in as one user in Tab A, open the "General" room.
  2. Log in as a second user (e.g. your superuser, in an incognito window) in Tab B, open the same room.
  3. Type a message in Tab A, hit Enter.
  4. Watch Tab B — the message appears instantly, with no refresh, and it's also now saved: refreshing either tab shows it in the message history rendered by views.py's room() view (Step 8).
  5. Open DevTools → Network → WS in either tab to watch the raw JSON frames flowing both ways — useful for confirming exactly what consumers.py is sending before touching the JavaScript at all.
If a message doesn't appear on the other tab

Work through it the same way as every earlier debugging step in this series: check the browser console first (a JS error there means the socket never opened, often a wrong URL path), then check the Django terminal (a Python traceback there points at consumers.py, most often a missing @database_sync_to_async around an ORM call).

Closing thesis

The pattern worth remembering

The build order splits cleanly into two halves that mirror each other. Knowing which of your two "views" — the HTTP one or the consumer — is responsible for which job is the whole design.

Steps 4–13 · Completely ordinary Django

model → migrate → admin → view → url → template, identical in shape to any other Django app. It would work fine — minus live updates — if the walkthrough stopped here.

Steps 14–17 · Exactly one new capability

A consumer, a WebSocket route, an ASGI router that can tell HTTP and WebSocket traffic apart, and the JavaScript to use it — layered on top without changing anything already built.

Channels doesn't replace Django's request/response model — it runs alongside it. Loading history is an HTTP job. Streaming what happens next is a WebSocket job. That split is the actual lesson.
