Building MindNotes — notes that find each other, with Django + a tiny Rust "AI"

"AI" here means something concrete: every note becomes a numeric vector describing what it's about, and vectors that sit close together represent notes that are about similar things. That's the whole engine behind semantic search and an automatic "Related Notes" list — no paid API, no internet access required.

  • Users write and edit notes (title + content)
  • Every save asks Rust to vectorize the text — Django stores the vector
  • Search turns your query into a vector too, ranks notes by similarity
  • Every note page shows "Related Notes," computed the same way
notes plotted by what they're about — closeness is computed, not tagged

Why embedding is a plain JSONField, not something more exotic

The vector is just a list of numbers (e.g. [0.12, -0.04, 0.31, ...]) — Postgres/SQLite can store that as JSON with zero extra setup. A production system with millions of notes would eventually want a real vector database (pgvector, Pinecone, etc.) for fast similarity search inside the database — but for a simple project, storing the vector and asking Rust to compare a handful of them on demand is more than fast enough, and far simpler to reason about.

Why null=True, blank=True on embedding

A note can legitimately exist with embedding=None — if the Rust service happens to be down the moment someone saves a note (Step 14 handles this gracefully), the note must still save successfully; it just won't show up in similarity results until it's re-saved or a background job fills it in later.

Step 14 — Open notes/views.py again — add create/edit, calling the AI service

notes/views.py
import requests
from django.conf import settings

def _get_embedding(text):
    try:
        response = requests.post(
            f'{settings.AI_SERVICE_URL}/embed',
            json={'text': text},
            timeout=2,
        )
        response.raise_for_status()
        return response.json()['vector']
    except requests.exceptions.RequestException:
        return None    # AI service down or unreachable — degrade gracefully

@login_required
def note_create(request):
    if request.method == 'POST':
        title = request.POST.get('title', '').strip()
        content = request.POST.get('content', '').strip()
        if title and content:
            note = Note.objects.create(author=request.user, title=title, content=content)
            note.embedding = _get_embedding(f'{title} {content}')
            note.save()
            return redirect('notes:note_detail', pk=note.pk)
    return render(request, 'notes/note_form.html')

@login_required
def note_edit(request, pk):
    note = get_object_or_404(Note, pk=pk, author=request.user)
    if request.method == 'POST':
        note.title = request.POST.get('title', '').strip()
        note.content = request.POST.get('content', '').strip()
        note.embedding = _get_embedding(f'{note.title} {note.content}')
        note.save()
        return redirect('notes:note_detail', pk=note.pk)
    return render(request, 'notes/note_form.html', {'note': note})
Why _get_embedding is its own small function

Both note_create and note_edit need the exact same "text in, vector out, fail safely" behavior — writing it once and calling it twice means a future change (a retry, a different timeout) only has to happen in one place.

Why it returns None on failure, instead of raising

Same defensive boundary as SocialSnap's like_post — saving a note is the essential feature; computing its embedding is an enhancement. If the AI service is down, unreachable, or slow, the note must still save with embedding=None rather than the whole page failing with a 500 error. This is exactly why Step 4 made embedding nullable.

Why the embedding is computed from title + content, not content alone

The title usually carries the strongest signal of what a note is about — including it in the text sent for vectorization makes the resulting vector a better summary of the note's topic.

notes/views.py
def note_detail(request, pk):
    note = get_object_or_404(Note, pk=pk, author=request.user)
    related_notes = []
    if note.embedding:
        candidates = Note.objects.filter(author=request.user).exclude(pk=note.pk).exclude(embedding=None)
        related_notes = _rank_by_similarity(note.embedding, candidates)[:3]
    return render(request, 'notes/note_detail.html', {'note': note, 'related_notes': related_notes})

@login_required
def search(request):
    query = request.GET.get('q', '').strip()
    results = []
    if query:
        query_vector = _get_embedding(query)
        if query_vector:
            candidates = Note.objects.filter(author=request.user).exclude(embedding=None)
            results = _rank_by_similarity(query_vector, candidates)
    return render(request, 'notes/search_results.html', {'query': query, 'results': results})

def _rank_by_similarity(query_vector, candidates):
    candidate_list = [{'id': n.id, 'vector': n.embedding} for n in candidates]
    if not candidate_list:
        return []
    try:
        response = requests.post(
            f'{settings.AI_SERVICE_URL}/similar',
            json={'query_vector': query_vector, 'candidates': candidate_list},
            timeout=2,
        )
        response.raise_for_status()
        ranked = response.json()['ranked']    # [{'id': 4, 'score': 0.87}, ...]
    except requests.exceptions.RequestException:
        return []

    notes_by_id = {n.id: n for n in candidates}
    scored_notes = []
    for entry in ranked:
        note = notes_by_id.get(entry['id'])
        if note:
            note.score = entry['score']    # attached at render time, not stored on the model
            scored_notes.append(note)
    return scored_notes

(Replace the earlier plain note_detail from Step 8 with this version — same URL, same name, now doing more.)

Why the similarity math is sent to Rust, not computed in a Python loop

This is the entire reason Rust exists in this project. A Python for loop computing similarity across hundreds or thousands of vectors is exactly the kind of numeric work Python is slow at and Rust is built for — sending the query vector and candidate vectors over HTTP and letting Rust do the comparison is the whole point of the split described at the top of this walkthrough.

Why note.score is a plain attribute, not a model field

The score only means something relative to one specific search or one specific note's related-notes lookup — it's not a property of the note itself the way title is. Attaching it just for this one render, on an object about to be handed straight to a template and then discarded, is the correct scope for a value this temporary.

Step 18 — Create src/vectorizer.rs (new file)

This is the "AI" in the smallest honest sense: turning text into a fixed-length numeric vector using feature hashing — a real, established technique (used in production systems like Vowpal Wabbit) that needs no pretrained model, no downloaded weights, and no internet access, while still producing vectors where similar text produces similar vectors.

src/vectorizer.rs
const VECTOR_SIZE: usize = 128;

/// Turns arbitrary text into a fixed-length vector by hashing each word into
/// one of VECTOR_SIZE buckets and counting occurrences, then normalizing.
pub fn embed_text(text: &str) -> Vec<f32> {
    let mut vector = vec![0f32; VECTOR_SIZE];

    for word in text.to_lowercase().split_whitespace() {
        let bucket = simple_hash(word) % VECTOR_SIZE;
        vector[bucket] += 1.0;
    }

    normalize(&mut vector);
    vector
}

fn simple_hash(word: &str) -> usize {
    let mut hash: usize = 5381;
    for byte in word.bytes() {
        hash = hash.wrapping_mul(33).wrapping_add(byte as usize);
    }
    hash
}

fn normalize(vector: &mut [f32]) {
    let magnitude: f32 = vector.iter().map(|v| v * v).sum::<f32>().sqrt();
    if magnitude > 0.0 {
        for v in vector.iter_mut() {
            *v /= magnitude;
        }
    }
}
Why every word hashes into a bucket instead of a full vocabulary dictionary

A real vocabulary-based approach needs to remember every word it's ever seen, which grows without bound and needs to be kept in sync between training and use. Hashing every word into one of a fixed 128 buckets means the vector size never changes no matter how much text flows through the system — the tradeoff (rare "collisions" where two different words share a bucket) is a well-known, acceptable one at this scale.

Why normalize() matters for the similarity step that comes next

Without normalizing, a long note would produce a vector with a bigger magnitude than a short note purely from having more words, which would make it look "similar to everything" regardless of actual topic. Normalizing every vector to length 1 means Step 19's cosine similarity is comparing direction (what the text is about) rather than length (how much text there was).

Step 19 — Create src/similarity.rs (new file)

src/similarity.rs
pub fn cosine_similarity(a: &[f32], b: &[f32]) -> f32 {
    let dot: f32 = a.iter().zip(b.iter()).map(|(x, y)| x * y).sum();
    dot    // both vectors are already normalized (Step 18), so dot product IS cosine similarity
}

pub struct ScoredId {
    pub id: i64,
    pub score: f32,
}

pub fn rank_by_similarity(query: &[f32], candidates: &[(i64, Vec<f32>)]) -> Vec<ScoredId> {
    let mut scored: Vec<ScoredId> = candidates
        .iter()
        .map(|(id, vector)| ScoredId {
            id: *id,
            score: cosine_similarity(query, vector),
        })
        .collect();

    scored.sort_by(|a, b| b.score.partial_cmp(&a.score).unwrap());
    scored
}
Why dot product alone equals cosine similarity here

The textbook formula for cosine similarity divides the dot product by both vectors' magnitudes — but since embed_text (Step 18) already normalized every vector to length 1, that division would just be dividing by 1 twice. Skipping the redundant division isn't a shortcut that sacrifices correctness; it's a direct consequence of a decision already made one file earlier. Worth noticing as a pattern: doing normalization once, early, made every later computation on that data simpler.

Why .partial_cmp(...).unwrap() instead of the more familiar .cmp()

Floating-point numbers in Rust don't implement a total ordering (because of NaN), so Vec<f32> can't use the simple .sort() a Vec<i64> could. partial_cmp handles the general case and .unwrap() is safe here specifically because normalized similarity scores can never actually be NaN.

Step 20 — Open src/main.rs

src/main.rs
mod vectorizer;
mod similarity;

use actix_web::{web, App, HttpServer, HttpResponse};
use serde::{Deserialize, Serialize};
use vectorizer::embed_text;
use similarity::rank_by_similarity;

#[derive(Deserialize)]
struct EmbedRequest {
    text: String,
}

#[derive(Serialize)]
struct EmbedResponse {
    vector: Vec<f32>,
}

async fn embed(payload: web::Json<EmbedRequest>) -> HttpResponse {
    let vector = embed_text(&payload.text);
    HttpResponse::Ok().json(EmbedResponse { vector })
}

#[derive(Deserialize)]
struct Candidate {
    id: i64,
    vector: Vec<f32>,
}

#[derive(Deserialize)]
struct SimilarRequest {
    query_vector: Vec<f32>,
    candidates: Vec<Candidate>,
}

#[derive(Serialize)]
struct RankedResult {
    id: i64,
    score: f32,
}

#[derive(Serialize)]
struct SimilarResponse {
    ranked: Vec<RankedResult>,
}

async fn similar(payload: web::Json<SimilarRequest>) -> HttpResponse {
    let candidates: Vec<(i64, Vec<f32>)> = payload
        .candidates
        .iter()
        .map(|c| (c.id, c.vector.clone()))
        .collect();

    let ranked = rank_by_similarity(&payload.query_vector, &candidates)
        .into_iter()
        .map(|r| RankedResult { id: r.id, score: r.score })
        .collect();

    HttpResponse::Ok().json(SimilarResponse { ranked })
}

#[actix_web::main]
async fn main() -> std::io::Result<()> {
    println!("AI service running on http://127.0.0.1:8080");

    HttpServer::new(|| {
        App::new()
            .route("/embed", web::post().to(embed))
            .route("/similar", web::post().to(similar))
    })
    .bind(("127.0.0.1", 8080))?
    .run()
    .await
}

Tracing both request paths through these three files:

Django POSTs { "text": "..." } to /embed → main.rs: embed() deserializes EmbedRequest → vectorizer.rs: embed_text() hashes words into buckets, normalizes → main.rs: returns { "vector": [...] } as JSON Django POSTs { "query_vector": [...], "candidates": [...] } to /similar → main.rs: similar() deserializes SimilarRequest → similarity.rs: rank_by_similarity() computes cosine similarity per candidate, sorts → main.rs: returns { "ranked": [{"id": 4, "score": 0.87}, ...] } as JSON

Closing thesis

The pattern worth remembering

The Rust side of this project earns its place for a genuinely different reason than SocialSnap's real-time service did. Both are legitimate reasons to reach for a second language — but they're not the same reason, and knowing which one applies is what tells you whether "add a Rust service" is solving a real problem, or just adding complexity for its own sake.

SocialSnap needed Rust because Python can't

Django can't efficiently keep thousands of WebSocket connections open and push to them concurrently without a much heavier setup (Channels + Redis). That's a concurrency limit, not a speed limit.

MindNotes needed Rust because Python is slow

Python can do vector math and text hashing just fine, functionally. It would just be slower doing it in a plain loop at any real scale — a throughput problem, not a capability problem.
