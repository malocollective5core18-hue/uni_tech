PART 00Unlearn This Habits worth dropping before they calcify — the document you gave me named these directly, so let's see exactly why each one hurts.
1

mysql_* functions vs. PDO

Old: the mysql_* function family. New: PDO with prepared statements. This isn't a style preference — mysql_* was fully removed from PHP years ago and simply doesn't exist anymore.

// old — this code CANNOT RUN on any current PHP version, the functions don't exist
$result = mysql_query("SELECT * FROM users WHERE id = " . $_GET['id']);

// new — works today, and doesn't concatenate raw user input into SQL
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);
2

Everything tangled in one file vs. separated concerns

Mixing HTML, PHP logic, and database calls in one file works for a 10-line script — and becomes unreadable fast. Compare the shape of both.

// tangled — HTML, DB query, and logic all interleaved
<?php $pdo = new PDO(...); $r = $pdo->query("SELECT * FROM products"); ?>
<ul><?php foreach ($r as $p) { ?><li><?= $p['name'] ?> - $<?= $p['price'] ?></li><?php } ?></ul>

// separated — config, logic, and display each in their own place
require 'config.php';
$products = get_active_products($pdo);   // logic lives in a function
// then a clean template just loops over $products
3

== vs === — the loose comparison trap

PHP's == coerces types before comparing, same trap as JavaScript's version — and PHP has a few of its own famous surprises.

0 == "abc"        // false in PHP 8+ (this was TRUE in PHP 7 — a real, historic gotcha)
"1" == "01"        // true  — both convert to the number 1
"10" == "1e1"      // true  — both convert to the number 10
100 == "1e2"       // true  — same reason
0 === "abc"        // false — no coercion, different types, done.
Why this changed between PHP versions

PHP 8 specifically fixed the 0 == "abc" case (it used to be true) because it was such a common source of bugs — a good reminder that even "loose" comparison behavior isn't fixed forever, and === sidesteps needing to track these changes at all.

4

Copy-pasted code vs. understanding the data

The same snippet, used two different ways — one copy-pasted without adjustment, one adapted because the data was actually understood first.

// copied from a tutorial about "users" without adjustment...
foreach ($products as $user) {          // wrong variable name, wrong mental model
    echo $user["email"];                 // products don't have emails — silent bug or crash
}

// understood — the loop variable name matches what's actually being looped over
foreach ($products as $product) {
    echo $product["name"] . ": $" . $product["price"];
}
5

Jumping to Laravel too early vs. plain PHP first

Laravel's Route::get(), Product::where(...), and Blade's {{ }} are all just organized wrappers around exactly the plain-PHP concepts in Parts 01–12. See the direct mapping.

Why this hub insists on plain PHP first

If a Laravel error ever comes from the layer underneath — a raw SQL problem, a form data quirk, a string-handling bug — recognizing it depends entirely on already knowing what's happening one level down. Laravel doesn't remove that layer, it just wraps it politely.

PART 00BThe XAMPP File System What's actually inside that installation, folder by folder — click through the real thing instead of taking it on faith.
🧩 Before you dive in
Five folders you'll actually touch, out of everything XAMPP installs.
  1. htdocs/ is your document root — anything Apache serves to a browser has to live inside it. This is the only folder most PHP beginners ever need to open.
  2. mysql/data/ is where MySQL physically stores every database's actual files — you'll rarely touch this directly, but it's why "stop XAMPP mid-write" can occasionally corrupt a database.
  3. php/php.ini is PHP's own configuration file — upload limits, error display, memory limits, and enabled extensions all live here, and changing it requires restarting Apache.
  4. apache/conf/httpd.conf configures the web server itself — port number, document root location, and (via included files) virtual hosts.
  5. phpMyAdmin/ is itself just a PHP application, sitting inside htdocs — that's literally why it's reachable at localhost/phpmyadmin.

Click through a real XAMPP installation

This is what's actually sitting in C:\xampp\ (or /opt/lampp/ on Linux) after installation — click any folder or file.

Inside htdocs/ — where your actual code lives

Everything under here maps directly to a URL — this is the folder you'll open in your code editor for every single project in this hub.

htdocs/

3

php.ini — the settings you'll actually need to change

Five lines out of thousands — these are the ones nearly every beginner ends up editing at some point.

upload_max_filesize = 40M     ; default is often too small for real file uploads
post_max_size = 40M            ; must be >= upload_max_filesize, or uploads silently fail
memory_limit = 256M            ; raise this if a script hits "Allowed memory size exhausted"
display_errors = On             ; helpful locally — turn Off in any real production environment
max_execution_time = 30          ; how long a script can run before PHP kills it
Don't forget to restart

php.ini is only read when Apache starts PHP — after editing it, you have to stop and restart Apache in the XAMPP Control Panel before the change takes effect.

Where MySQL actually keeps your data

phpMyAdmin is a friendly window onto files sitting in mysql/data/ — worth knowing this exists, even though you'll interact with it through phpMyAdmin almost always.

PART 01Structure & Output The absolute starting point — how a .php file becomes a web page at all.
🧩 Before you dive in
Five things worth knowing before the labs below.
  1. A PHP file is normal text/HTML with <?php ... ?> blocks mixed in — anything inside those tags runs on the server; everything outside is sent to the browser as-is.
  2. echo is how PHP sends text to the page being built — it's the most-used statement in this entire hub.
  3. The server (Apache, via XAMPP) runs the PHP and sends back plain HTML — by the time it reaches a browser, none of the PHP code itself is visible, only its output.
  4. A line ends with a semicolon ; — leaving one off is the single most common beginner syntax error.
  5. Comments (//, #, /* */) are never sent to the browser — they exist purely for whoever reads the code next.
1

Your first echo

Save this as index.php inside your XAMPP htdocs folder and open it in a browser — this is the whole file.

<?php
echo "Hello, world!";
localhost/myfirst/index.php
2

echo vs. print — and combining multiple values

Both send text to the page. echo can take several comma-separated values in one call; print always takes exactly one and returns 1 (rarely useful, but worth knowing it exists).

echo "One", " ", "Two", " ", "Three";   // echo can take multiple, comma-separated
print "Just one string";                  // print takes exactly one
localhost/myfirst/echo_test.php
3

Mixing HTML and PHP inline

You can hop in and out of PHP mode as many times as you need in one file — this is how PHP got its name (PHP: Hypertext Preprocessor).

<h1>Welcome</h1>
<p>Today is <?php echo date("Y-m-d"); ?></p>
<p>You have <?php echo 3 + 4; ?> new messages.</p>
localhost/myfirst/welcome.php
4

String concatenation with the dot operator

PHP glues strings together with . — easy to confuse with + if you're coming from another language.

$first = "Alice";
$last = "Smith";
echo $first . " " . $last;          // "Alice Smith"
echo $first + $last;                 // NOT string joining — PHP tries to add them as numbers
5

print_r() and var_dump() — actually seeing what's inside a variable

echo can't display an array directly. print_r() shows its structure readably; var_dump() goes further and shows exact types too.

$user = ["name" => "Alice", "age" => 28];

echo $user;         // Warning: Array to string conversion — NOT what you want
print_r($user);      // Array ( [name] => Alice [age] => 28 )
var_dump($user);      // array(2) { ["name"]=> string(5) "Alice" ["age"]=> int(28) }
6

Comments — three styles, same purpose

None of these ever reach the browser — they're stripped out before output is sent.

// single line, C++ style — most common
# single line, shell style — less common, same effect
/* multi
   line
   block */
echo "This is the only thing a visitor ever sees.";
localhost/myfirst/comments.php
PART 02Variables & Types Every variable starts with $ — and the associative array is the single most important data shape in all of PHP.
🧩 Before you dive in
PHP's type system, in five points.
  1. Every variable name starts with $ — $name, $age, $isActive.
  2. PHP is dynamically typed — you don't declare a type up front; it's inferred from whatever value you assign, and can change if you reassign a different type later.
  3. The core types you'll use constantly: string (text), int, float, bool, array, and null (explicitly "no value").
  4. An indexed array is a numbered list: ["a", "b", "c"]. An associative array uses named keys instead: ["name" => "Alice"] — this is PHP's version of a dictionary/object.
  5. Inside double-quoted strings, "$name" is automatically replaced with the variable's value — single-quoted strings '$name' do NOT do this substitution.
1

Declaring the four core scalar types

No type keyword needed — PHP figures out the type from the value itself.

$name = "Alice";          // string
$age = 28;                 // integer
$price = 19.99;             // float
$is_active = true;           // boolean

var_dump($name, $age, $price, $is_active);
2

Indexed arrays — an ordered list

Square brackets, comma-separated, accessed by position starting at 0 — same as most languages.

$items = ["apple", "banana", "orange"];
echo $items[0];       // "apple"
echo count($items);    // 3
$items[] = "grape";     // append to the end
3

Associative arrays — PHP's dictionary

The => arrow pairs a key with a value — this shape is everywhere: form data, database rows, config, JSON.

$user = [
    "name" => "Alice",
    "email" => "alice@example.com",
    "active" => true
];

echo $user["name"];    // "Alice"
4

gettype() — checking what type you're actually holding

Useful when debugging "why isn't this comparison working" — often the answer is that a value is a string when you expected a number.

$age = "28";              // note: a STRING, not an integer, easy to do by accident (e.g. from a form)
echo gettype($age);        // "string"
echo gettype((int) $age);   // "integer" — after casting
5

Double quotes vs. single quotes — the $variable difference

This trips up nearly everyone at least once — the two quote styles are NOT interchangeable when a variable is involved.

$name = "Alice";
echo "Hello, $name!";     // "Hello, Alice!" — double quotes interpolate
echo 'Hello, $name!';      // "Hello, $name!" — single quotes print it literally
6

Type juggling — when PHP converts types for you, uninvited

PHP will often convert types automatically during math or comparison — usually convenient, occasionally the exact source of a confusing bug.

$quantity = "5";        // a string, maybe straight from a form
$total = $quantity * 3;   // PHP converts "5" to 5 automatically for the multiplication
echo $total;               // 15 — works, but only because the string LOOKED like a number

$bad = "five" * 3;          // this can't be converted — TypeError in modern PHP
PART 03Decisions (if / elseif / else) How PHP branches — the mechanism behind every "show this, not that" choice a script makes.
🧩 Before you dive in
Five building blocks for branching logic.
  1. if runs a block only when its condition evaluates to true. elseif checks another condition if the first was false. else catches everything else.
  2. Use === (identical to Part 00's lesson) whenever possible — it compares both value and type, with no surprise conversions.
  3. && (AND) requires both sides true. || (OR) requires at least one side true.
  4. The ternary operator condition ? valueIfTrue : valueIfFalse is a compact if/else that produces a value directly, instead of running a whole block.
  5. switch is useful once you're comparing one variable against many possible fixed values — cleaner than a long elseif chain in that specific case.
1

Basic if / else

Straight from the source document's own example — a service status check.

$status = "running";

if ($status === "running") {
    echo "Service is healthy";
} else {
    echo "Something's wrong";
}
2

elseif chains

Each condition is checked in order, top to bottom — the first one that's true wins, and the rest are skipped entirely.

$status = "stopped";

if ($status === "running") {
    echo "Service is healthy";
} elseif ($status === "stopped") {
    echo "Need to restart";
} else {
    echo "Unknown status – check logs";
}
3

=== vs. == in a real condition

Watch a login-style check behave differently depending on which operator guards it.

$userInputId = "0";       // came in as a string, e.g. from a URL
$adminId = 0;               // stored as an integer

if ($userInputId == $adminId) { echo "Loose match — treated as admin!"; }    // true — risky
if ($userInputId === $adminId) { echo "Strict match — different types, not equal"; }  // false — safe
4

&& and || — combining conditions

A common real check: can this user actually check out?

$cartHasItems = true;
$isLoggedIn = true;
$canCheckout = $cartHasItems && $isLoggedIn;    // both required

$isStudent = false;
$isSenior = true;
$getsDiscount = $isStudent || $isSenior;         // either is enough
5

The ternary operator

A compact if/else, used constantly inline inside strings and function arguments.

$age = 20;
$status = $age >= 18 ? "adult" : "minor";
echo "Status: $status";
6

switch — one variable, several fixed possibilities

Cleaner than a long elseif chain when you're comparing one thing against a list of exact values.

switch ($role) {
    case "admin":
        echo "Full access";
        break;
    case "editor":
        echo "Can edit content";
        break;
    default:
        echo "Read-only access";
}
Why break matters

Forgetting break lets execution "fall through" into the next case — sometimes intentional, usually a bug. Modern PHP also supports match as a stricter, safer alternative that doesn't need break at all.

PART 04Loops Processing collections — the tool that scales from 3 items to 3 million with the same few lines.
🧩 Before you dive in
Four loop shapes, and two ways to control them mid-run.
  1. foreach is the loop you'll use most in PHP — it walks every item of an array directly, no index counting required.
  2. for is best when you need a specific numeric range or a counter — for ($i = 1; $i <= 5; $i++).
  3. while keeps looping as long as its condition stays true — you're responsible for eventually making that condition false, or it runs forever.
  4. break exits a loop completely, right now. continue skips just the current iteration and moves to the next.
  5. foreach over an associative array gives you both the key and the value: foreach ($user as $key => $value).
1

foreach over an indexed array

Straight from the source document — checking a list of servers.

$servers = ["web1", "web2", "db1"];

foreach ($servers as $server) {
    echo "Checking $server...<br>";
}
2

foreach over an associative array — key AND value

Adding $key => before the value variable gives you both at once.

$user = ["name" => "Alice", "email" => "alice@example.com", "active" => true];

foreach ($user as $key => $value) {
    echo "$key: $value\n";
}
3

for loop — counting with precision

Three parts: starting value, the condition that keeps it going, and what happens after each round.

for ($i = 1; $i <= 5; $i++) {
    echo "Round $i\n";
}
4

while loop — repeat until a condition flips

No built-in counter step — you have to remember to change the condition yourself, or the loop never ends.

$count = 0;
while ($count < 3) {
    echo "while: $count\n";
    $count++;    // without this line, the loop never ends
}
5

break — stopping a loop entirely

The moment PHP hits break, it exits the loop right then — nothing after it in that loop runs again.

for ($i = 1; $i <= 10; $i++) {
    if ($i === 4) {
        break;
    }
    echo "$i\n";
}
// prints 1, 2, 3 — then stops completely
6

continue — skipping just one round

Unlike break, the loop keeps going — it just skips whatever's left in that one iteration.

for ($i = 1; $i <= 5; $i++) {
    if ($i === 3) {
        continue;
    }
    echo "$i\n";
}
// prints 1, 2, 4, 5 — 3 is skipped, but the loop still finishes
PART 05Functions The single most important habit for turning scripts into systems — if you copy the same lines twice, it's time for a function.
🧩 Before you dive in
Five things about PHP functions worth knowing before writing your own.
  1. function name(...) { ... } defines a reusable block — call it anytime by name with name(...).
  2. return hands a value back to whoever called the function — without it, calling the function gives you null.
  3. Default parameters — function greet($name = "friend") — let an argument be optional, falling back to the default if omitted.
  4. Type hints (PHP 7+) let you declare what type a parameter or return value should be: function greet(string $name): string — PHP will throw an error if the wrong type is passed.
  5. Functions can accept arrays as arguments just like any other value — this is how most real data actually flows through a PHP app.
1

A basic function, with return

Straight from the source document — the simplest possible reusable function.

function greet($name) {
    return "Hello, " . $name;
}

echo greet("Alice");
echo greet("Bob");
2

A default parameter

Leave the argument out entirely, and the default kicks in automatically.

function greet($name = "friend") {
    return "Hello, " . $name . "!";
}

echo greet();          // uses the default
echo greet("Zara");    // overrides it
3

Multiple parameters

As many as needed, comma-separated, in a fixed order.

function calculateTotal($price, $quantity, $taxRate = 0.08) {
    $subtotal = $price * $quantity;
    return $subtotal + ($subtotal * $taxRate);
}

echo calculateTotal(19.99, 3);
4

Passing an array into a function

Arrays flow into functions exactly like any other value — this is the shape you'll use once real data (from a form, a file, a database) is involved.

function countActive($users) {
    $count = 0;
    foreach ($users as $user) {
        if ($user["active"]) { $count++; }
    }
    return $count;
}

$users = [["name" => "Alice", "active" => true], ["name" => "Bob", "active" => false]];
echo countActive($users);
5

Before/after — spotting repeated code that should become a function

The exact rule from the source document: copy the same 5–10 lines more than twice, and it's time to extract a function.

// before — the same formatting logic repeated three times
echo "$" . number_format(19.99, 2);
echo "$" . number_format(5.5, 2);
echo "$" . number_format(120, 2);

// after — one function, called three times
function formatPrice($amount) { return "$" . number_format($amount, 2); }
echo formatPrice(19.99);
echo formatPrice(5.5);
echo formatPrice(120);
6

Type hints — catching mistakes before they run

A modern PHP habit: declare what types go in and out. PHP enforces it and throws a real error on mismatch, the same "catch it early" philosophy as Dart's null safety.

function greet(string $name): string {
    return "Hello, $name!";
}

echo greet("Amara");     // works fine
echo greet(42);            // TypeError: greet(): Argument #1 ($name) must be of type string, int given
PART 06Arrays The heart of PHP data — lists of records are exactly the shape that comes back from databases and APIs.
🧩 Before you dive in
The array functions you'll reach for constantly.
  1. A "list of records" — an indexed array of associative arrays — is the shape almost all real data takes: rows from a database, results from an API, items in a form.
  2. array_map($fn, $array) transforms every item and returns a new array — same length, same idea as JavaScript's .map().
  3. array_filter($array, $fn) keeps only the items where $fn returns true — same idea as .filter().
  4. count() tells you how many items are in an array. sort() and usort() reorder it, the latter with a custom comparison function.
  5. Arrays can nest arbitrarily deep — an array inside an array inside an array — and you access deeper levels by chaining [key] repeatedly.
1

A list of records — straight from the source document

This exact shape — array of associative arrays — is what a database query returns in Part 09.

$users = [
    ["id" => 1, "name" => "Alice", "active" => true],
    ["id" => 2, "name" => "Bob", "active" => false]
];

foreach ($users as $user) {
    if ($user["active"]) {
        echo $user["name"] . "<br>";
    }
}
2

array_map() — transform every item

Same shape as JavaScript's .map() — a new array back, same length, every item transformed the same way.

$prices = [19.99, 5.50, 120, 8.25];
$withTax = array_map(fn($p) => round($p * 1.08, 2), $prices);
print_r($withTax);
3

array_filter() — keep only what matches

Same idea as .filter() — the callback decides, item by item, what survives into the new array.

$users = [["name" => "Alice", "active" => true], ["name" => "Bob", "active" => false], ["name" => "Zara", "active" => true]];
$active = array_filter($users, fn($u) => $u["active"]);
print_r($active);
4

count() and sort()

Two of the most-used array functions in any real script.

$scores = [88, 42, 95, 67];
echo count($scores);     // 4
sort($scores);              // sorts in place, ascending
print_r($scores);
5

usort() — sorting by a custom rule

Plain sort() can't sort an array of associative arrays meaningfully — usort() takes a comparison function so you decide the rule.

$products = [["name" => "Mouse", "price" => 24.99], ["name" => "Monitor", "price" => 220]];
usort($products, fn($a, $b) => $a["price"] <=> $b["price"]);   // cheapest first
print_r($products);
6

Nested arrays — going several levels deep

Chain [key] access repeatedly to reach deeply nested data — very common with JSON from APIs.

$company = [
    "name" => "Acme",
    "hq" => ["city" => "Nairobi", "country" => "Kenya"]
];

echo $company["hq"]["city"];    // "Nairobi"
PART 07Handling Forms The moment a script starts talking to a real user — and the exact place security actually matters.
🧩 Before you dive in
Five things about form handling, including the one that prevents XSS.
  1. An HTML <form> with method="POST" sends its fields to whatever action URL is specified — PHP receives them in the $_POST superglobal array.
  2. $_GET holds data sent via the URL's query string (?name=Alice) — visible in the address bar, used for things like search or filters.
  3. $_POST["name"] ?? "Guest" is the safe pattern from the source document — the ?? (null coalescing) provides a fallback if the field was never actually submitted.
  4. htmlspecialchars() is not optional — any time you echo something a user typed back onto the page, wrap it in this function, or you've opened an XSS hole.
  5. Server-side validation (checking required fields aren't empty, etc.) has to happen in PHP — client-side HTML/JS validation can always be bypassed by a motivated visitor.
1

A simple form → $_POST

Type a name, submit, and watch process.php receive exactly what was typed.

<!-- form.php -->
<form method="POST" action="process.php">
    Name: <input type="text" name="name">
    <button type="submit">Send</button>
</form>

<?php // process.php
$name = $_POST["name"] ?? "Guest";
echo "Hello, " . htmlspecialchars($name);
localhost/myfirst/process.php
2

?? fallback — what happens when nothing was submitted

Submit the form empty and see exactly why ?? "Guest" matters.

$name = $_POST["name"] ?? "Guest";
echo "Hello, " . htmlspecialchars($name);

// without the ?? fallback:
$name = $_POST["name"];    // Warning: Undefined array key "name" — if the field wasn't sent at all
3

htmlspecialchars() — watch the XSS actually get blocked

Same real vulnerability as ever — try submitting a name that's actually a script tag, with and without the protection.

// unsafe — never do this
echo "Hello, " . $_POST["name"];

// safe — the source document's exact recommendation
echo "Hello, " . htmlspecialchars($_POST["name"]);
localhost/myfirst/process.php
4

$_GET vs. $_POST

Same underlying idea — user-submitted data — arriving through two different channels, one visible in the URL, one not.

// a GET-based search — visible in the URL: search.php?q=laptop
$query = $_GET["q"] ?? "";

// a POST-based login — NOT visible in the URL, better for sensitive data
$password = $_POST["password"] ?? "";
5

Reading several fields from one form

A real form usually has more than one field — each becomes its own key in $_POST.

$name = $_POST["name"] ?? "";
$email = $_POST["email"] ?? "";
$message = $_POST["message"] ?? "";

echo "New contact from " . htmlspecialchars($name) . " (" . htmlspecialchars($email) . ")";
6

Basic validation — the required-field check

Before saving or processing anything, check the essentials are actually present.

$name = trim($_POST["name"] ?? "");

if ($name === "") {
    echo "Name is required.";
} else {
    echo "Thanks, " . htmlspecialchars($name) . "!";
}
PART 08Files & JSON Storage The lightweight alternative to a database — good enough for config, small datasets, and quick prototypes.
🧩 Before you dive in
Five functions that cover most file-based storage needs.
  1. json_encode($data) turns a PHP array into a JSON string — add JSON_PRETTY_PRINT as a second argument for human-readable formatting.
  2. file_put_contents($path, $data) writes a string to a file, creating it if it doesn't exist, overwriting if it does.
  3. file_get_contents($path) reads a file's entire contents as a string. json_decode($string, true) turns that JSON string back into a PHP array (the true matters — without it, you get an object instead of an array).
  4. file_exists($path) checks before you try to read something that might not be there — avoids a warning/crash.
  5. This whole pattern only makes sense for small, infrequently-updated data — Part 09's real database exists specifically for anything bigger or more concurrent.
1

Writing JSON to a file

Straight from the source document — turning a PHP array into a saved file.

$data = ["name" => "Alice", "role" => "admin"];
file_put_contents("user.json", json_encode($data, JSON_PRETTY_PRINT));
2

Reading it back

json_decode(..., true) — that true is what makes you get a familiar PHP array back, not a stdClass object.

$loaded = json_decode(file_get_contents("user.json"), true);
echo $loaded["name"];
3

JSON_PRETTY_PRINT — readable vs. compact

Same data, two formattings — pretty for humans debugging a file, compact for actual transmission over a network.

echo json_encode($data);                        // compact, one line
echo json_encode($data, JSON_PRETTY_PRINT);        // indented, readable
4

Overwriting stored data

file_put_contents replaces the entire file by default — worth knowing before you accidentally lose data.

$data = json_decode(file_get_contents("user.json"), true);
$data["role"] = "superadmin";                                    // update in memory
file_put_contents("user.json", json_encode($data, JSON_PRETTY_PRINT));   // save the whole file again
5

file_exists() — checking before you read

Reading a file that isn't there produces a warning and an empty result — checking first avoids that entirely.

if (file_exists("settings.json")) {
    $settings = json_decode(file_get_contents("settings.json"), true);
} else {
    $settings = ["theme" => "light"];    // sensible default
}
6

Appending a new record to stored JSON

Read, modify the array in memory, write the whole thing back — there's no partial-append for JSON, unlike a plain text log file.

$users = json_decode(file_get_contents("users.json"), true) ?? [];
$users[] = ["name" => "Zara", "role" => "editor"];
file_put_contents("users.json", json_encode($users, JSON_PRETTY_PRINT));
PART 09PDO & the Database The foundation of almost every real PHP application — and the exact place SQL injection either gets prevented or doesn't.
🧩 Before you dive in
PDO in five points — treat this part as the payoff for Part 00's mysql_* lesson.
  1. PDO (PHP Data Objects) is PHP's modern, unified way to talk to a database — works with MySQL, PostgreSQL, SQLite, and others through the same interface.
  2. new PDO("mysql:host=localhost;dbname=testdb", "root", "") opens the connection — host, database name, username, password.
  3. Prepared statements — $pdo->prepare("... WHERE id = ?") then $stmt->execute([$id]) — send your query and your data separately, so user input can never be interpreted as part of the SQL itself.
  4. fetchAll(PDO::FETCH_ASSOC) returns query results as exactly the "array of associative arrays" shape from Part 06.
  5. Every one of INSERT, SELECT, UPDATE, and DELETE should use prepared statements with ? placeholders — never build a query by concatenating a variable straight into the SQL string.
1

Connecting to the database

One line, and PHP has a live connection to MySQL, running via XAMPP.

$pdo = new PDO("mysql:host=localhost;dbname=testdb", "root", "");
2

INSERT with a prepared statement

The ? placeholders are filled in by execute(), safely — this is the exact pattern from the source document.

$stmt = $pdo->prepare("INSERT INTO users (name, email) VALUES (?, ?)");
$stmt->execute(["Alice", "alice@example.com"]);
3

SELECT + fetchAll

Reading every row back out, as the familiar array-of-arrays shape.

$stmt = $pdo->query("SELECT * FROM users");
$users = $stmt->fetchAll(PDO::FETCH_ASSOC);

foreach ($users as $user) {
    echo $user["name"] . " - " . $user["email"] . "<br>";
}
4

Why prepared statements stop SQL injection

The exact same malicious input, run against a concatenated query vs. a prepared one — watch the difference in what actually executes.

// unsafe — user input concatenated directly into SQL
$name = $_GET['name'];   // e.g. "'; DROP TABLE users; --"
$pdo->query("SELECT * FROM users WHERE name = '$name'");   // the attacker's SQL runs too

// safe — the value is sent separately, never interpreted as SQL syntax
$stmt = $pdo->prepare("SELECT * FROM users WHERE name = ?");
$stmt->execute([$name]);   // treated purely as a value, no matter what it contains
5

UPDATE

Same prepared-statement shape — placeholders for both the new value and the WHERE condition.

$stmt = $pdo->prepare("UPDATE users SET email = ? WHERE name = ?");
$stmt->execute(["alice.new@example.com", "Alice"]);
6

DELETE

The most irreversible of the four — always double-check the WHERE clause, since a query with no condition deletes every row.

$stmt = $pdo->prepare("DELETE FROM users WHERE email = ?");
$stmt->execute(["alice@example.com"]);
Why a missing WHERE clause is a genuine production disaster

DELETE FROM users with no WHERE deletes every single row in the table, instantly, with no built-in confirmation. This is exactly the kind of mistake senior engineers develop a reflex to double-check before ever pressing enter on a real database.

PART 10Sessions How a stateless protocol (HTTP) manages to remember who you are across multiple page loads.
🧩 Before you dive in
The mechanism behind every "logged in" state you've ever seen.
  1. HTTP itself has no memory — every page request is independent. Sessions are PHP's way of bridging that gap, storing data on the server tied to one visitor.
  2. session_start() must run before any other session code, on every single page that needs to read or write session data — easy to forget, and the most common session bug.
  3. $_SESSION is a superglobal array, just like $_POST — write to it, and PHP remembers it for that visitor's next page load.
  4. isset($_SESSION["user_id"]) is the standard way to check "is someone actually logged in" before showing protected content.
  5. session_destroy() clears everything — the standard way to implement logout.
1

Starting a session and storing data

Straight from the source document — the moment a "login" actually happens, in the simplest possible form.

session_start();
$_SESSION["user_id"] = 5;
$_SESSION["name"] = "Alice";
2

Reading session data on a different page

This is the whole point — data set on one page load is still there on the next, as long as session_start() runs both times.

// dashboard.php — a completely separate page load
session_start();
echo "Welcome, " . $_SESSION["name"];
localhost/myfirst/dashboard.php
3

isset() — checking if someone is actually logged in

The standard guard at the top of any page that shouldn't be visible to a logged-out visitor.

session_start();
if (isset($_SESSION["user_id"])) {
    echo "Welcome back!";
} else {
    echo "Please log in first.";
}
4

session_destroy() — logging out

Clears the stored session data — after this, isset() checks on protected pages fail again, exactly as if the visitor never logged in.

session_start();
session_destroy();
echo "You have been logged out.";
5

Gating a whole page behind a session check

The pattern nearly every "members only" page actually uses — redirect logic first, real content second.

session_start();
if (!isset($_SESSION["user_id"])) {
    echo "Redirecting to login...";
    exit;   // stop the script here — nothing below this line runs
}
echo "Here's your private dashboard, " . $_SESSION["name"];
6

Sessions vs. cookies — the one-sentence distinction

Related but different mechanisms — worth being precise about which is which.

Why sessions still need a cookie under the hood

PHP typically stores session data on the server, but it still sends the visitor's browser a small cookie containing just a session ID — that ID is what lets PHP match the next request back to the right stored session data. Sessions and cookies aren't really rivals; sessions are built on top of one cookie.

PART 11Organizing Code Splitting one file into several — the habit that prepares you directly for how Laravel structures everything.
🧩 Before you dive in
require, include, and the difference that matters.
  1. require "file.php" pulls another file's code into the current one — if that file is missing, PHP stops with a fatal error.
  2. include "file.php" does the same thing, but only produces a warning (not a fatal error) if the file is missing — the script keeps running.
  3. require_once / include_once guarantee a file is only loaded one time, even if it's required from multiple places — prevents "cannot redeclare function" errors.
  4. A common pattern: a config.php file holding shared settings (database credentials, constants), require'd at the top of every file that needs them.
  5. Variables defined in an included file become available in the file that included it — this is exactly how config.php's variables end up usable in main.php.
1

require vs. include — what happens when the file is missing

Same missing file, two very different consequences.

require "missing_file.php";     // Fatal error — script stops completely, right here
echo "This line never runs.";

include "missing_file.php";      // Warning only — script keeps going
echo "This line DOES run.";
2

The config.php pattern

Straight from the source document — shared settings live in one file, used everywhere.

// config.php
$db_host = "localhost";
$db_name = "testdb";
$db_user = "root";
$db_pass = "";

// main.php
require "config.php";
echo "Connecting to $db_name on $db_host...";
3

require_once — avoiding duplicate loading

If two different files both try to require the same third file, plain require loads it twice — often crashing on "function already defined."

// helpers.php defines: function formatPrice($n) { ... }

require_once "helpers.php";   // loaded once
require_once "helpers.php";   // recognized as already loaded — skipped safely, no error
4

Before/after — splitting one tangled file into pieces

The direct payoff of Part 00's "unlearn tangled files" lesson, shown as an actual file tree.

5

Passing data between included files

An included file can also read variables that were already defined before it was included — data flows both directions.

// main.php
$pageTitle = "My Dashboard";
require "header.php";

// header.php — can use $pageTitle, because it's included AFTER that line
echo "<title>$pageTitle</title>";
6

A preview of autoloading — what Composer/Laravel does instead

Manually require-ing every single file gets unwieldy fast — this is the exact problem Composer's autoloader (and Laravel, built on it) solves automatically.

// plain PHP — every file needed, manually
require "models/User.php";
require "models/Product.php";
require "services/EmailService.php";
// ...times fifty, in a real app

// with Composer's autoloader (one line, once)
require "vendor/autoload.php";
// now ANY class in your project is available automatically, no manual requiring
PART 12Basic Error Handling Real systems fail — databases go down, files go missing. This part is about failing safely instead of crashing ugly.
🧩 Before you dive in
try/catch, in five points.
  1. try { ... } catch (ExceptionType $e) { ... } — code that might fail goes in try; what to do if it fails goes in catch.
  2. Different failure types throw different exception classes — PDOException for database errors specifically, which lets you catch database problems without accidentally swallowing unrelated bugs.
  3. $e->getMessage() gives you the actual error text — useful for logging, but risky to show a visitor directly (it can leak internal details).
  4. finally { ... } runs no matter what — whether the try block succeeded or an exception was caught — good for cleanup that must always happen.
  5. You can throw your own exceptions from your own functions, to signal a specific failure the calling code should handle.
1

Basic try/catch

Straight from the source document — catching a failed database connection.

try {
    $pdo = new PDO("mysql:host=localhost;dbname=testdb", "root", "wrongpassword");
} catch (PDOException $e) {
    echo "Database connection failed: " . $e->getMessage();
}
2

Catching a specific exception type

Catching PDOException specifically means an unrelated bug elsewhere doesn't get silently swallowed by the same catch block.

try {
    $result = 10 / 0;   // a different kind of error — DivisionByZeroError
} catch (PDOException $e) {
    echo "This won't catch it — wrong exception type";
} catch (DivisionByZeroError $e) {
    echo "Caught the right one: " . $e->getMessage();
}
3

A friendly message vs. leaking the real error

A real security consideration — the raw error can reveal your database structure or file paths to anyone who triggers it.

try {
    $pdo = new PDO("mysql:host=localhost;dbname=testdb", "root", "wrongpassword");
} catch (PDOException $e) {
    // unsafe — shown to any random visitor
    echo $e->getMessage();   // "SQLSTATE[HY000] [1045] Access denied for user 'root'@'localhost'..."

    // safe — log the real detail privately, show something generic publicly
    error_log($e->getMessage());
    echo "Something went wrong. Please try again later.";
}
4

finally — code that always runs

Whether the try block succeeded or the catch block fired, finally runs either way — perfect for cleanup.

try {
    echo "Attempting operation...\n";
    throw new Exception("Something failed");
} catch (Exception $e) {
    echo "Caught: " . $e->getMessage() . "\n";
} finally {
    echo "Cleanup runs no matter what.\n";
}
5

Throwing your own exception

Your own functions can signal a specific failure the caller has to deal with, rather than returning something ambiguous like false or null.

function withdraw($balance, $amount) {
    if ($amount > $balance) {
        throw new Exception("Insufficient funds");
    }
    return $balance - $amount;
}

try {
    echo withdraw(100, 500);
} catch (Exception $e) {
    echo "Transaction failed: " . $e->getMessage();
}
6

Why suppressing errors with @ is a trap, not a fix

PHP lets you silence a warning with @ in front of an expression — this hides the symptom while leaving the actual bug completely untouched.

// suppressed — the warning disappears, but $data is still null, and nothing downstream knows why
$data = @file_get_contents("might_not_exist.json");

// handled properly — the actual problem is checked for and dealt with
if (file_exists("might_not_exist.json")) {
    $data = file_get_contents("might_not_exist.json");
} else {
    $data = null;
    error_log("Config file missing: might_not_exist.json");
}
Why this closes the loop back to Part 00

@ is the error-handling equivalent of copy-pasting code without understanding it — it makes a symptom invisible without ever addressing the actual cause, which usually just means the same bug resurfaces somewhere else, harder to trace.

PART 13Structuring a Real PHP Project Part 11 taught you to split files apart — this is the full blueprint for where everything actually goes once a project has more than three files.
🧩 Before you dive in
The five ideas that turn "a folder of PHP files" into "a real project."
  1. A public/ folder, separate from the rest of the project, holding only what Apache should actually be able to serve directly — everything else (your real logic, config, credentials) sits outside it, unreachable by URL.
  2. composer.json is PHP's project manifest — declares your dependencies (like Laravel does) and, critically, sets up autoloading so you never write a manual require for your own classes again.
  3. A .env file holds secrets and environment-specific settings (database passwords, API keys) — and is never committed to version control, unlike config.php which often was.
  4. A single entry point (public/index.php) that every request flows through is called the front controller pattern — it's exactly what Laravel, and nearly every modern framework, does under the hood.
  5. This structure isn't arbitrary — it's the exact shape Laravel's own project layout takes, just built by hand first so none of it is mysterious later.
1

A real, well-organized PHP project — click through it

This is the direct evolution of Part 11's config.php/helpers.php habit, taken all the way.

📁 src/
📁 config/
📁 views/
📁 vendor/ (generated by Composer)
📄 .env
📄 .gitignore
📄 composer.json

2

Why public/ exists — the security reason, made concrete

Point Apache's document root at the project root instead of public/, and this happens.

# WRONG — document root = my-app/ itself
http://localhost/my-app/.env                    # your database password, served as plain text!
http://localhost/my-app/config/database.php      # your actual config file, downloadable

# RIGHT — document root = my-app/public/
http://localhost/.env                             # 404 Not Found — it's outside the document root
3

composer.json and PSR-4 autoloading

This one config block is what lets you write new App\Models\User() anywhere in the project with zero manual require statements — Composer maps namespaces to folders automatically.

{
    "autoload": {
        "psr-4": { "App\\": "src/" }
    }
}

// after running "composer dump-autoload", this just works from anywhere:
require "vendor/autoload.php";
$user = new App\Models\User();   // Composer finds src/Models/User.php automatically
4

.env vs. config.php — why secrets moved out

Same data, different lifecycle — one gets committed to git, one absolutely must not.

# .env — different on every machine (local, staging, production), NEVER committed
DB_PASSWORD=my-real-secret-password

# config/database.php — committed to git, reads FROM .env, contains no actual secrets
return ['password' => $_ENV['DB_PASSWORD']];
5

The front controller pattern — one file, every request

Instead of a separate .php file per page, every URL routes through public/index.php, which decides what to do based on the URL itself — this is the exact mechanism Route::get() is built on top of.

// public/index.php — literally every request hits this one file
$path = $_SERVER['REQUEST_URI'];

if ($path === '/products') {
    require '../src/pages/products.php';
} elseif ($path === '/contact') {
    require '../src/pages/contact.php';
} else {
    http_response_code(404);
    echo "Page not found";
}
This is Laravel's routes/web.php, before Laravel existed

Every Route::get('/products', ...) call you'll write in Part 14 is doing exactly this if/elseif chain — just organized into a clean list instead of a growing chain of conditions, and handling far more edge cases than this simplified version does.

The mental model, named

Move data. Make decisions. Talk to storage. Everything else is packaging.

Every one of the 103 labs above was really practicing the same four moves, over and over, in different combinations: get data in (forms, files, a database), decide something about it (if/else, validation), transform it (functions, arrays), and get a result back out (echo, JSON, a saved row). Laravel doesn't add a fifth move — it just gives the existing four a clean, consistent home.

  • Why "unlearn mysql_*" mattered before anything else. A tool that's been removed from the language can't be a foundation for anything — Part 00 cleared that away first so everything built after it would actually still work today.
  • Why arrays showed up in nearly every part after Part 06. Form data, JSON files, and database rows all arrive in PHP as the exact same shape — an array, often of associative arrays. Once that shape is second nature, three "different" topics turn out to be one.
  • Why htmlspecialchars() and prepared statements are really the same idea. Both exist because untrusted input (from a form, from a URL) can never be treated as safe code or safe SQL — only ever as data. Blade's auto-escaping and Eloquent's query builder are Laravel doing this same thing for you, automatically.
