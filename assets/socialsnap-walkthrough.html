Building SocialSnap

A simple social media system: Django runs the actual app, and a small Rust / Actix-web sidecar pushes live updates to open browser tabs. No theory dump — just the build order: which file gets opened or created, what goes inside it, and why it had to happen right then.

Django never breaks because Rust is down. Rust only ever adds the live-update layer on top.

Why two languages/frameworks, not just Django? Everything here — accounts, posts, follows, the feed — is regular request/response work Django is great at. The one thing Django's synchronous default setup handles badly is pushing live updates to open browser tabs (e.g. "someone just liked this post, update the count without a page refresh"). Doing that properly in Django means Django Channels + an ASGI server + Redis — a real jump in complexity. Actix-web is built around async and WebSockets from the ground up, so a tiny standalone Rust service handles that one job well, while Django keeps doing everything it's already good at.

This is the real-world pattern: a Python/Django monolith with a small Rust "sidecar" service for the one feature that genuinely benefits from it — not a rewrite of the whole app.

Django handles

  • Registration / login
  • Profiles
  • Follow / unfollow
  • Creating a post
  • A feed of posts from people you follow
  • Liking a post

Actix-web handles

  • A WebSocket endpoint browsers connect to
  • An HTTP endpoint Django calls to broadcast "this post's like count changed" to every connected browser, live

from django.db import models
from django.contrib.auth.models import User

class Profile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE)
    bio = models.CharField(max_length=200, blank=True)
    avatar = models.ImageField(upload_to='avatars/', blank=True, null=True)

    def __str__(self):
        return self.user.username


class Follow(models.Model):
    follower = models.ForeignKey(User, related_name='following', on_delete=models.CASCADE)
    following = models.ForeignKey(User, related_name='followers', on_delete=models.CASCADE)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        unique_together = ('follower', 'following')

    def __str__(self):
        return f"{self.follower} → {self.following}"
Why related_name='following'/'followers' on the same model pointing at the same User: without explicit related_names, Django can't tell "people following me" from "people I follow" — both would collide on the same default reverse name. This is what lets Step 9's feed query read as request.user.following.all() — self-explanatory instead of a generic queryset.

unique_together again, same reasoning as the school project's Enrollment model: prevent following the same person twice at the database level, not just hope the view remembers to check.

accounts/views.py
python
from django.shortcuts import render, redirect, get_object_or_404
from django.contrib.auth import login, logout
from django.contrib.auth.decorators import login_required
from django.contrib.auth.forms import UserCreationForm, AuthenticationForm
from django.contrib.auth.models import User
from django.views.decorators.http import require_POST
from .models import Profile, Follow

def register(request):
    if request.method == 'POST':
        form = UserCreationForm(request.POST)
        if form.is_valid():
            user = form.save()
            Profile.objects.create(user=user)
            login(request, user)
            return redirect('posts:feed')
    else:
        form = UserCreationForm()
    return render(request, 'accounts/register.html', {'form': form})

def login_view(request):
    if request.method == 'POST':
        form = AuthenticationForm(request, data=request.POST)
        if form.is_valid():
            login(request, form.get_user())
            return redirect('posts:feed')
    else:
        form = AuthenticationForm()
    return render(request, 'accounts/login.html', {'form': form})

@require_POST
def logout_view(request):
    logout(request)
    return redirect('posts:feed')

@login_required
def profile(request, username):
    target = get_object_or_404(User, username=username)
    is_following = Follow.objects.filter(follower=request.user, following=target).exists()
    return render(request, 'accounts/profile.html', {'target': target, 'is_following': is_following})

@require_POST
@login_required
def toggle_follow(request, username):
    target = get_object_or_404(User, username=username)
    if target != request.user:
        follow, created = Follow.objects.get_or_create(follower=request.user, following=target)
        if not created:
            follow.delete()
    return redirect('accounts:profile', username=username)

if target != request.user in toggle_follow is the same category of check as the school project's teacher-owns-course lookup — a simple guard against a nonsensical or abusable state (a user following themselves), caught before it ever reaches the database.

Step 16Open posts/views.py again — add liking, with a stubbed-out real-time call
python
import requests
from django.conf import settings
from django.views.decorators.http import require_POST
from .models import Post, Like

@require_POST
@login_required
def like_post(request, post_id):
    post = get_object_or_404(Post, id=post_id)
    like, created = Like.objects.get_or_create(user=request.user, post=post)
    if not created:
        like.delete()
    likes_count = post.likes.count()

    try:
        requests.post(
            f'{settings.REALTIME_SERVICE_URL}/notify',
            json={'post_id': post.id, 'likes_count': likes_count},
            timeout=1,
        )
    except requests.exceptions.RequestException:
        pass   # the like itself must still succeed even if the realtime service is offline

    return redirect('posts:feed')
Why the try/except around requests.post, specifically: liking a post is the core feature; broadcasting that like to other open tabs is an enhancement. If the Rust service is down, restarting, or not built yet (exactly the situation we're in right now, mid-walkthrough), liking a post must still work. This mirrors the "don't let a non-essential dependency take down an essential feature" principle, applied here across a network boundary instead of within one process.

Step 19Create src/broadcaster.rs (new file)

The "who's currently connected, and how do I tell all of them something" piece — built first because both the WebSocket handler (Step 20) and the HTTP /notify handler (Step 21) depend on it existing.

rust
use actix::prelude::*;
use std::collections::HashMap;

/// A single text message pushed out to one connected browser.
#[derive(Message)]
#[rtype(result = "()")]
pub struct BroadcastMessage(pub String);

/// Sent by a new WebSocket session when it connects, to register itself.
#[derive(Message)]
#[rtype(result = "usize")]
pub struct Connect {
    pub addr: Recipient<BroadcastMessage>,
}

/// Sent when a WebSocket session closes, to clean up.
#[derive(Message)]
#[rtype(result = "()")]
pub struct Disconnect {
    pub id: usize,
}

/// Sent by the HTTP /notify handler — "tell everyone this post's like count changed."
#[derive(Message)]
#[rtype(result = "()")]
pub struct PostUpdate(pub String);

pub struct Broadcaster {
    sessions: HashMap<usize, Recipient<BroadcastMessage>>,
    next_id: usize,
}

impl Broadcaster {
    pub fn new() -> Self {
        Broadcaster { sessions: HashMap::new(), next_id: 0 }
    }
}

impl Actor for Broadcaster {
    type Context = Context<Self>;
}

impl Handler<Connect> for Broadcaster {
    type Result = usize;

    fn handle(&mut self, msg: Connect, _ctx: &mut Context<Self>) -> usize {
        let id = self.next_id;
        self.next_id += 1;
        self.sessions.insert(id, msg.addr);
        id
    }
}

impl Handler<Disconnect> for Broadcaster {
    type Result = ();

    fn handle(&mut self, msg: Disconnect, _ctx: &mut Context<Self>) {
        self.sessions.remove(&msg.id);
    }
}

impl Handler<PostUpdate> for Broadcaster {
    type Result = ();

    fn handle(&mut self, msg: PostUpdate, _ctx: &mut Context<Self>) {
        for addr in self.sessions.values() {
            addr.do_send(BroadcastMessage(msg.0.clone()));
        }
    }
}
Why a HashMap<usize, Recipient<...>> instead of just a Vec: each connected browser needs a stable ID so Disconnect can remove exactly that one session when a tab closes, without accidentally dropping a different, still-open connection.
Why this is an Actor at all, instead of a plain shared Mutex<Vec<...>>: actix actors process one message at a time by design, which means Connect/Disconnect/PostUpdate can never race against each other corrupting the sessions map — thread-safety comes from the actor model itself, without writing any manual locking code.
Step 20Create src/ws_session.rs (new file)

The other half: what happens inside one browser's WebSocket connection.

rust
use actix::prelude::*;
use actix_web_actors::ws;
use crate::broadcaster::{Broadcaster, BroadcastMessage, Connect, Disconnect};

pub struct WsSession {
    pub id: usize,
    pub broadcaster: Addr<Broadcaster>,
}

impl Actor for WsSession {
    type Context = ws::WebsocketContext<Self>;

    fn started(&mut self, ctx: &mut Self::Context) {
        let addr = ctx.address();
        self.broadcaster
            .send(Connect { addr: addr.recipient() })
            .into_actor(self)
            .then(|res, act, _ctx| {
                if let Ok(id) = res {
                    act.id = id;
                }
                fut::ready(())
            })
            .wait(ctx);
    }

    fn stopped(&mut self, _ctx: &mut Self::Context) {
        self.broadcaster.do_send(Disconnect { id: self.id });
    }
}

/// Messages coming FROM the Broadcaster, pushed OUT to this one browser.
impl Handler<BroadcastMessage> for WsSession {
    type Result = ();

    fn handle(&mut self, msg: BroadcastMessage, ctx: &mut Self::Context) {
        ctx.text(msg.0);
    }
}

/// Raw WebSocket protocol events coming FROM the browser.
impl StreamHandler<Result<ws::Message, ws::ProtocolError>> for WsSession {
    fn handle(&mut self, msg: Result<ws::Message, ws::ProtocolError>, ctx: &mut Self::Context) {
        match msg {
            Ok(ws::Message::Ping(bytes)) => ctx.pong(&bytes),
            Ok(ws::Message::Close(reason)) => {
                ctx.close(reason);
                ctx.stop();
            }
            // Browsers in this project only listen; they never send anything meaningful back.
            _ => {}
        }
    }
}
Why started() registers with the broadcaster instead of the broadcaster discovering sessions on its own: actix has no built-in way to "list every open WebSocket" — each session has to actively announce itself when it starts and clean up after itself when it stops. This is the direct Rust-actor equivalent of a Python object registering a callback and unregistering it in a finally block.
Why the StreamHandler mostly does nothing (_ => {}): this project's browsers are read-only listeners — all the writing happens through Django's /notify HTTP call in Step 21, not through the WebSocket itself. A chat app would fill this in to broadcast whatever the user typed; a like-counter doesn't need to.
Step 21Open src/main.rs

Wire the two pieces above into an actual running server, and add the HTTP endpoint Django calls.

rust
mod broadcaster;
mod ws_session;

use actix::prelude::*;
use actix_web::{web, App, HttpServer, HttpRequest, HttpResponse, Error};
use actix_web_actors::ws;
use serde::Deserialize;

use broadcaster::{Broadcaster, PostUpdate};
use ws_session::WsSession;

#[derive(Deserialize)]
struct NotifyPayload {
    post_id: i64,
    likes_count: i64,
}

async fn ws_index(
    req: HttpRequest,
    stream: web::Payload,
    broadcaster: web::Data<Addr<Broadcaster>>,
) -> Result<HttpResponse, Error> {
    ws::start(
        WsSession { id: 0, broadcaster: broadcaster.get_ref().clone() },
        &req,
        stream,
    )
}

async fn notify(
    payload: web::Json<NotifyPayload>,
    broadcaster: web::Data<Addr<Broadcaster>>,
) -> HttpResponse {
    let message = serde_json::json!({
        "post_id": payload.post_id,
        "likes_count": payload.likes_count,
    })
    .to_string();

    broadcaster.do_send(PostUpdate(message));
    HttpResponse::Ok().finish()
}

#[actix_web::main]
async fn main() -> std::io::Result<()> {
    let broadcaster_addr = Broadcaster::new().start();

    println!("Realtime service running on http://127.0.0.1:8080");

    HttpServer::new(move || {
        App::new()
            .app_data(web::Data::new(broadcaster_addr.clone()))
            .route("/ws/", web::get().to(ws_index))
            .route("/notify", web::post().to(notify))
    })
    .bind(("127.0.0.1", 8080))?
    .run()
    .await
}

Tracing the two request paths through these three files:

Browser opens ws://127.0.0.1:8080/ws/ → main.rs: ws_index() → ws_session.rs: WsSession::started() → Broadcaster gets a Connect message → registered Django POSTs to http://127.0.0.1:8080/notify → main.rs: notify() deserializes NotifyPayload → broadcaster.rs: Broadcaster receives PostUpdate → loops every registered session → ws_session.rs: each WsSession's Handler<BroadcastMessage> fires → ctx.text(msg) → browser receives it

Terminal — build and run it:

<script>
    const socket = new WebSocket('ws://127.0.0.1:8080/ws/');

    socket.onmessage = function (event) {
        const data = JSON.parse(event.data);
        const counter = document.getElementById(`like-count-${data.post_id}`);
        if (counter) {
            counter.textContent = data.likes_count;
        }
    };

    socket.onclose = function () {
        console.log('Realtime connection closed — like counts will update on refresh instead.');
    };
</script>
{% endblock %}

This is only added to feed.html, not base.html directly — the feed page is the only place like-count-<id> elements exist, so it's the only page that needs a live socket open. Every other page (profile, create post) has no use for it.

Why id="like-count-${data.post_id}" in the JS matches id="like-count-{{ post.id }}" from Step 15 exactly: this is the one piece of "shared contract" between Django and Rust — neither service imports the other's code, so the only way they agree on anything is by both sides independently using the same naming convention. If you ever rename one side's ID pattern without the other, this is the first thing to check when live updates silently stop working.

That last check is the most important one in the whole system: it proves the architectural boundary from the top of this document actually holds — Django's job is never allowed to fail because Rust's job failed.

The pattern worth remembering

Inside Django, the loop is identical to both earlier projects: model → migrate → admin (seed data) → view → url → template, with every template link built ahead of its target and the target following immediately after.

The new idea this project adds is the boundary between two services. Django was written first and works completely on its own; Rust was added second, purely additive, and every place they touch — the REALTIME_SERVICE_URL setting, the try/except around the HTTP call, the matching like-count-<id> naming convention — was written defensively, assuming the other side might not be there.

That's the actual skill in a polyglot system: not making two languages talk to each other, but making sure one half never breaks because the other half did.
