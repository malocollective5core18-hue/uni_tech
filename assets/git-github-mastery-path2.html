01
Local basics

Commits & History

Goal: internalize that a commit is a snapshot, and that Git tracks changes over time, not just current file state.

Run it

  1. Create a folder, run git init, confirm with git status.
  2. Configure identity: git config --global user.name "..." and user.email.
  3. Create notes.txt with one line. git status shows it as untracked.
  4. git add notes.txt, then git status again — now staged.
  5. git commit -m "Add initial notes".
  6. Add a second line, run git status — now modified, not staged.
  7. Commit that too. Compare git log vs git log --oneline.
  8. Make 3 more small commits, one change each, with a real message each time.
bash — practice-repo
git initInitialized empty Git repository in ~/practice-repo/.git/ echo "First line of notes" > notes.txt git statusOn branch main No commits yet Untracked files: notes.txt git add notes.txt git statusChanges to be committed: new file: notes.txt git commit -m "Add initial notes"[main (root-commit) a1c9e02] Add initial notes 1 file changed, 1 insertion(+) create mode 100644 notes.txt echo "Second line" >> notes.txt git statusChanges not staged for commit: modified: notes.txt git add . && git commit -m "Add second line to notes"[main 7f3b118] Add second line to notes 1 file changed, 1 insertion(+) git log --oneline7f3b118 Add second line to notes a1c9e02 Add initial notes

Working directory — before step 3

practice-repo/
└── .git/          (empty repo)

Working directory — after step 8

practice-repo/
├── .git/
│   └── (5 commits in history)
└── notes.txt   ← tracked, 5 lines
What git log --oneline actually shows you
Each dot is a full snapshot. HEAD just points at the latest one — the others don't vanish.
Checkpoint question If you delete notes.txt right now with rm notes.txt, is your data actually gone? (No — it's still in every commit before the deletion. Be able to explain why in one sentence before moving on.)
Common pitfall Writing vague commit messages ("fix", "update", "asdf") during practice because "it's just practice." Build the real habit now — "Fix off-by-one error in pagination loop" is the actual skill; typing git commit -m correctly is not.
02
The three areas

Staging & Undoing

Goal: stop thinking of Git as one step ("save") and start seeing the three distinct areas — working directory, staging area, commit history — because every undo command only makes sense once you know which area it operates on.

The three areas, and which command moves you which way
reset moves changes back but keeps them. checkout -- / restore throws them away for good.

Run it

bash — practice-repo
echo "Third line" >> notes.txt git diffdiff --git a/notes.txt b/notes.txt+Third line git add notes.txt && git diff(nothing — the diff moved) git diff --staged+Third line echo "oops, bad edit" >> notes.txt git restore notes.txt(the bad edit is gone — permanently) git add notes.txt && git reset notes.txtUnstaged changes after reset: M notes.txt(still in working dir — check with git diff) git commit -am "Add third line"[main d4e9a01] Add third line git commit --amend -m "Add third line to notes.txt"[main 9b2f120] Add third line to notes.txt git revert 9b2f120[main 3aa701c] Revert "Add third line to notes.txt" 1 file changed, 1 deletion(-)
Checkpoint question What's the practical difference between git checkout -- file and git reset file, in terms of which area each one touches? Write the answer yourself before checking a reference.
Common pitfall Confusing reset (moves changes back toward working, doesn't delete them) with checkout --/restore (actually discards them). This confusion is exactly how people lose real work — practice the distinction now, on throwaway files.
03
Branching

Branching & Merge Conflicts

Goal: get comfortable branching and get comfortable with a real merge conflict — most juniors panic the first time they see conflict markers because they've never deliberately caused one on purpose in a safe environment.

Run it

  1. git checkout -b feature-a
  2. On feature-a, edit line 1 of notes.txt, commit.
  3. git checkout main, edit that same line 1 differently, commit.
  4. git merge feature-a — this will conflict on purpose.
  5. Open the file, resolve the <<<<<<< markers by hand, delete them.
  6. git add notes.txt, git commit (accept the pre-filled merge message).
  7. git log --all --graph to see it visually.
  8. git branch -D feature-a
bash — merge conflict
git checkout -b feature-aSwitched to a new branch 'feature-a' sed -i '1s/.*/Line 1 — rewritten on feature-a/' notes.txt git commit -am "Rewrite line 1 for feature-a"[feature-a e5c210f] Rewrite line 1 for feature-a git checkout mainSwitched to branch 'main' sed -i '1s/.*/Line 1 — updated on main/' notes.txt git commit -am "Update line 1 on main"[main 1c88a02] Update line 1 on main git merge feature-aAuto-merging notes.txt CONFLICT (content): Merge conflict in notes.txt Automatic merge failed; fix conflicts and then commit the result.

notes.txt — mid-conflict

Line 1 — updated on main
=======
Line 1 — rewritten on feature-a
>>>>>>> feature-a
Second line
Third line

notes.txt — resolved & committed

feature-a's rewrite
Second line

← markers deleted, file staged & committed
git log --all --graph after the merge
B and F both touched line 1 of the same file — that's the exact condition that forces a conflict instead of an auto-merge.
Checkpoint question Why did this conflict happen? (Two branches changed the same lines of the same file. Different files, or different lines of the same file, merge automatically without asking you.)
Common pitfall Panicking and running git merge --abort the first time markers appear, then avoiding branching altogether. Do this until resolving a conflict feels boring, not scary.
04
Remotes

GitHub & Remotes

Goal: understand that GitHub is just one remote copy of your repository — not a fundamentally different tool — and get comfortable with the fetch/pull/push cycle.

Local repo ↔ origin (GitHub)
GitHub isn't special magic — it's a remote your local repo talks to over these three commands.
bash — connect to GitHub
git remote add origin https://github.com/you/practice-repo.git git remote -vorigin https://github.com/you/practice-repo.git (fetch) origin https://github.com/you/practice-repo.git (push) git push -u origin mainEnumerating objects: 12, done. Writing objects: 100% (12/12), done. (full history included)
Checkpoint question What's the actual difference between git fetch and git pull? If your answer doesn't mention that pull = fetch + merge, revisit this section before continuing.
Common pitfall Treating git push as "save to the cloud" without expecting it can be rejected because the remote has commits you don't have locally. Deliberately trigger this once, read the rejection message, git pull, then push again.
05
Team workflow

Feature Branch Workflow & Pull Requests

Goal: practice the actual workflow used at almost every real company — not just the commands, but the sequence and reasoning behind them.

Two PRs racing on the same line — the second one conflicts
Fix: merge main into the PR-2 branch locally, resolve, push — the resolution lives on the branch where it's still reviewable.

Run it — the conflict-resolution half

bash — resolving a PR-level conflict
git checkout main git pull origin mainFast-forward, main is up to date git checkout your-second-branch git merge mainCONFLICT (content): Merge conflict in notes.txt Automatic merge failed; fix conflicts and then commit the result. <edit notes.txt, remove markers, keep the right content> git add notes.txt git commit -m "Merge main into your-second-branch, resolve conflict"[your-second-branch 6de881a] Merge main into your-second-branch, resolve conflict git push origin your-second-branch... PR page now shows "This branch has no conflicts with the base branch"
Checkpoint question Why merge main into the feature branch, rather than the other way around? (So the merge commit and its conflict resolution live on the feature branch, where a teammate can still review it via the PR, instead of landing directly on main unreviewed.)
Common pitfall Resolving PR conflicts entirely in GitHub's web editor without ever practicing the local resolution — fine for trivial conflicts, but real conflicts in application code need your actual editor and the ability to run the code to verify the fix.
06
Advanced git

Stash, Cherry-Pick, Rebase, Bisect

Goal: these are the commands that separate "I know Git" from "I can get myself out of trouble with Git" — each one solves a specific real situation, so practice them in that situation, not in isolation.

Stash — "I need to switch branches right now"

bash — stash
<editing notes.txt, unfinished, not committed> git stashSaved working directory and index state WIP on main: 6de881a Merge main... git statusnothing to commit, working tree clean git checkout other-branch<...do what you needed...> git checkout main git stash liststash@{0}: WIP on main: 6de881a Merge main... git stash popDropped stash@{0} — your unfinished edit is back, exactly as you left it
Four tools, four rescue situations

Cherry-pick — "I need just that one fix"

bash — cherry-pick
git log feature-b --onelinec4a119e Unrelated feature start 7dd2a01 Fix null-check bug in parser git checkout main git cherry-pick 7dd2a01[main 8ea310b] Fix null-check bug in parser Date: ... (original author date preserved)← only that one change landed on main

Interactive rebase — squash 4 sloppy commits into 1

bash — rebase -i
git log --oneline4d0a2f1 done 9c8e120 actually fix it 1b7f004 fix typo e2a910c wip git rebase -i HEAD~4pick e2a910c wip squash 1b7f004 fix typo squash 9c8e120 actually fix it squash 4d0a2f1 done <editor prompts for one combined message> git log --onelinea90cd33 Add pagination to results list← 4 messy commits are now 1 clean one

Bisect — "which of 50 commits broke it"

bash — bisect
git bisect start git bisect badcurrent commit marked bad git bisect good a1c9e02Bisecting: 5 revisions left to test after this (roughly 3 steps) <test the checked-out commit> git bisect goodBisecting: 2 revisions left to test (roughly 1 step) <test again> git bisect badc88de41 is the first bad commit git bisect reset
Checkpoint question For each of the four tools above, could you explain to someone else when to reach for it — not just what it does — in one sentence?
Common pitfall Learning rebase -i and immediately wanting to rewrite history on a branch other people have already pulled — never rebase commits that have been pushed and shared, only your own local, not-yet-shared work (this is why Phase 5's conflict resolution used merge, not rebase, once a PR was already open).

Checkpoint question If a new teammate cloned your practice repo right now with zero context, could they understand what it is and get it running from the README and commit history alone?
Common pitfall Treating clean history as something to fix "later" — it compounds the same way messy code does; the habit has to form during the small, low-stakes commits, not get retrofitted onto a large tangled history.
08
Guardrails

Production Readiness

Goal: everything so far worked on a solo practice repo with no consequences. Production repos add guardrails specifically because mistakes there have real cost — get familiar with the guardrails themselves, not just the commands.

Branch protection + CI, in one picture
The rule isn't personal discipline — it's enforced by the platform regardless of a moment of forgetfulness.

Run it

  1. GitHub → Settings → Branches → protect main: require a PR, require it up to date.
  2. Create a hook: copy .git/hooks/pre-commit.sample → pre-commit, chmod +x, make it echo "Running pre-commit checks...".
  3. Tag a release: git tag -a v1.0.0 -m "First stable version", git push origin v1.0.0.
  4. Simulate a leaked secret in a commit — research (don't necessarily run) git filter-repo, and understand the real first move is rotate the credential, not just delete the commit.
  5. Add .github/workflows/test.yml that runs echo "tests would run here" on every push — watch it in the Actions tab.
.github/workflows/test.yml
name: test on: [push] jobs: run-tests: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: echo "tests would run here"
bash — trying to bypass the protection
git checkout main && git commit -am "quick fix" && git push! [remote rejected] main -> main (protected branch hook declined) error: failed to push some refs← this is the feature working, not a bug
Checkpoint question Why is "require a PR before merging to main" a meaningfully different safety net than just personally deciding to always open PRs? (It's enforced regardless of forgetfulness, tiredness, or urgency.)
Common pitfall Treating branch protection, hooks, and CI as "senior developer concerns" to learn later. They're cheap to set up on a practice repo now — build the muscle memory before you're on a real team.

Capstone

Simulate a Real Production Hotfix

This combines everything above into one realistic scenario: a bug slips into production, and you fix it without losing the fix when ongoing work eventually merges.

main / develop / hotfix — the full incident, branch by branch
Step 7 is the one people forget — without it, develop can reintroduce the bug when it eventually merges into main.
  1. main = production. Create develop, add a couple of in-progress commits there.
  2. The incident: deliberately commit a bug directly to main.
  3. git checkout -b hotfix/fix-critical-error main
  4. Fix it, commit with a clear incident/fix message.
  5. Open a PR into main, merge it (protection rules and all, from Phase 8).
  6. git tag -a v1.0.1 -m "Hotfix: critical error in X"
  7. Critical step people forget — merge the fix back into develop:
bash — don't lose the fix
git checkout develop git merge mainMerge made by the 'recursive' strategy. app.js | 1 + 1 file changed, 1 insertion(+)
  1. Resolve any conflicts that come up (there may not be any — check).
  2. Write a one-paragraph incident summary: what broke, how it was caught, how it was fixed, what would prevent it next time.
If you can do all nine steps without opening a reference sheet You've internalized the actual workflow this document was building toward — not just the commands, but the judgment of which ones to reach for, in what order, under real conditions.
Final mastery checklist

Check each box only once you've actually done it

Not just read about it. Every item below maps back to an exercise above.

Local Git

  • Made commits and can explain staging vs. working directory from memory
  • Used git diff and git diff --staged to inspect changes before committing
  • Used checkout/restore, reset, revert, and commit --amend — and can explain when each is correct
  • Created, switched, and deleted branches confidently

Conflicts

  • Deliberately caused and resolved a merge conflict, start to finish, without panicking
  • Resolved a conflict inside an open pull request, correctly merging main into the feature branch

GitHub & Remotes

  • Connected a local repo to GitHub and pushed/pulled/fetched/cloned
  • Opened, reviewed, and merged a real pull request
  • Experienced and recovered from a rejected push

Advanced Tools

  • Used stash to context-switch without losing work
  • Used cherry-pick to move one specific commit between branches
  • Used interactive rebase to clean up messy commits before sharing them
  • Used bisect to find a bug-introducing commit

Team & Production Practices

  • Wrote consistently clear commit messages and branch names
  • Set up .gitignore before, not after, sensitive/build files got tracked
  • Enabled branch protection and watched it actually block a direct push
  • Created a Git hook and a minimal CI workflow
  • Tagged a release
  • Completed the hotfix capstone end to end, including merging the fix back into ongoing work
Once every box is checked, you're not just someone who's read about Git — you're someone who has broken it, fixed it, and built the judgment to know which tool a given real situation calls for. That judgment, not command recall, is what "production-ready" actually means.
