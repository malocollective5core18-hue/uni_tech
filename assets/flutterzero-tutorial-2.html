PART 00What Flutter Actually Is Before any code — the handful of ideas everything else in this page assumes you already have.
🧩 Before you dive in — the vocabulary
Six words you'll see constantly from here on, defined once, properly.
  1. Flutter is a toolkit from Google for building apps from one codebase that run natively on iOS, Android, web, and desktop — "natively" meaning it's not a website wrapped in an app shell, it's real compiled code.
  2. Dart is the programming language Flutter apps are written in — created by Google specifically to pair with Flutter. If you know JavaScript, Dart will feel very familiar; Part 01 covers exactly where they differ.
  3. A widget is Flutter's name for "a piece of UI" — but in Flutter, everything is a widget: not just buttons and text, but padding, alignment, and even the app itself. There's no separate "layout language" like HTML/CSS — it's all just widgets nested inside widgets.
  4. The widget tree is the nested structure that results — a screen is really one big tree of widgets, each one wrapping or sitting next to others, all the way down to individual pixels.
  5. Hot reload is a Flutter-specific feature: change your code while the app is running, and the change appears on screen in under a second — without losing whatever state the app was in (Demo 3 below shows exactly what that means).
  6. Cross-platform here means genuinely one codebase — not "mostly one codebase with platform-specific exceptions everywhere." Flutter draws every pixel itself rather than relying on each platform's native UI components, which is exactly why the same code looks identical on iOS and Android.

How Flutter draws, vs. how most cross-platform tools draw

Most "cross-platform" tools take your code and translate it into each platform's real native buttons and text fields. Flutter does something different — worth seeing the difference directly.

Why this is the actual reason Flutter looks identical everywhere

A tool that wraps native iOS/Android components will always look slightly different on each platform, because it's really using each platform's own UI kit underneath. Flutter skips that entirely — it has its own rendering engine and paints every pixel itself, the same way on every platform, which is also why a Flutter button doesn't automatically look "iOS-native" or "Android-native" unless you tell it to (Part 07 covers this choice).

6

Declarative UI vs. imperative UI — why Flutter code reads differently

Older UI toolkits are usually imperative: you give step-by-step instructions to mutate what's already on screen. Flutter is declarative: you describe what the screen should look like right now, for the current data, and Flutter figures out the steps.

// imperative (not how Flutter works) — step-by-step mutation
label.setText("5 items");
label.setColor(Colors.red);
if (count > 10) { label.setBold(true); }

// declarative (how Flutter actually works) — describe the end result for the current state
Text(
  '$count items',
  style: TextStyle(color: Colors.red, fontWeight: count > 10 ? FontWeight.bold : FontWeight.normal),
)
Why this explains so much of Flutter at once

This single idea is why setState exists (Part 05) — you never manually update a label's text; you change the underlying data and let build() re-describe the whole screen from scratch, every time.

PART 01Dart Essentials for Flutter If JavaScript is familiar, most of this will feel like a dialect — here's exactly where Dart differs, and why those differences exist.
🧩 Before you dive in — Dart vs. JavaScript, side by side
Not a full language course — just the handful of differences that actually show up in every Flutter file you'll write.
  1. Dart is statically typed — a variable's type is fixed when it's declared and checked before the app even runs, unlike JavaScript where a variable can hold anything, anytime.
  2. var in Dart still infers a fixed type from the first value — it's not the free-for-all var from old JavaScript. final is Dart's const — assign once, never reassign. const in Dart is stricter still: the value must be knowable at compile time.
  3. Null safety — a plain String name in Dart can never be null; if it might be, you write String? name. The compiler enforces this, which eliminates an entire category of crashes JavaScript happily allows.
  4. Classes are Dart's core building block — every widget you write is a class. Dart's class syntax will look familiar if you've seen classes in any typed language.
  5. Named parameters — Dart functions (and especially widget constructors) commonly use {curly braces} to accept arguments by name instead of position, e.g. Text('hi', style: myStyle) — this is everywhere in Flutter code.
  6. async/await work exactly like JavaScript's version — same keywords, same idea: pause this function until the awaited thing resolves.
1

var, final, const — Dart's three declarations

All three exist in Dart too, but the rules are stricter than JavaScript's version of the same names.

var age = 25;        // type is inferred as int, and locked in — age = 'old' would be an error
final name = 'Amara'; // like JS const: assign once, never reassign
const pi = 3.14159;    // like final, but must be a compile-time constant

age = 26;        // fine — var can be reassigned, as long as the type matches
// name = 'Kofi'; // error — final can't be reassigned
// const now = DateTime.now(); // error — DateTime.now() isn't knowable at compile time
2

Null safety — the ? that stops a whole category of crashes

In Dart, a variable can only ever be null if you explicitly said it's allowed to be, using ? after the type. Toggle between a safe and unsafe declaration below.

String name = 'Amara';   // can NEVER be null — Dart guarantees this at compile time
// name = null;          // this line would fail to even compile

String? nickname;        // the ? means "this is allowed to be null"
print(nickname);         // null — totally fine, we said it could be

// safely reading a value that might be null:
print(nickname?.toUpperCase() ?? 'no nickname set');
Familiar, on purpose

If Part 02 of Unlearn.js's optional chaining (?.) rings a bell — that's not a coincidence. Dart's ?. and ?? work identically to JavaScript's. Dart just takes it a step further by making the type declaration itself say whether null is even allowed in the first place.

3

Classes — the shape every widget you write will have

A Dart class bundles data and behavior together. Every single Flutter widget — including ones you write yourself — is a class that looks roughly like this.

class Person {
  String name;
  int age;

  Person(this.name, this.age);   // a constructor — runs when you create a new Person

  String greet() {
    return 'Hi, I\'m $name and I\'m $age years old.';
  }
}

final amara = Person('Amara', 25);
print(amara.greet());
4

Named parameters — how you'll actually call widget constructors

Curly braces in a function signature mean "these arguments are passed by name, not by position" — you'll type this pattern constantly once real Flutter widgets show up in Part 03.

void greet({required String name, String greeting = 'Hello'}) {
  print('$greeting, $name!');
}

greet(name: 'Amara');                          // uses the default greeting
greet(name: 'Kofi', greeting: 'Welcome');       // order doesn't matter, since they're named
greet(greeting: 'Hey', name: 'Zara');           // this works too — same result
Why required matters

Marking a named parameter required means Dart won't even compile if you forget to pass it — the same "catch it before it ships" philosophy as null safety, applied to function calls instead of variables.

Loops — for, for-in, and while, Dart-style

Almost identical to JavaScript's loops — the small syntax differences are worth seeing directly.

for (final fruit in fruits) { print(fruit); }   // Dart's for-in, like JS's for...of

int count = 0;
while (count < 3) { print('while: $count'); count++; }

List, Map, Set — Dart's three built-in collections

A List is Dart's array. A Map is Dart's object/dictionary — key-value pairs. A Set is a list that automatically removes duplicates.

List fruits = ['apple', 'banana', 'grape'];
fruits.add('mango');

Map user = {'name': 'Amara', 'age': 25};

Set uniqueNumbers = {1, 2, 2, 3, 3, 3};

String interpolation — $variable and ${expression}

You've already seen $name throughout this page — here's the full picture, including when the curly braces are actually required.

final age = 25;

PART 02The Project File System Every Flutter project you'll ever open has this exact same shape — click through a real one below instead of just reading a list.
🧩 Before you dive in — why the structure looks like this
Running flutter create my_app generates all of this automatically — here's the reasoning behind the biggest pieces.
  1. lib/ is where your actual app code lives — nearly everything you personally write goes here. It's short for "library."
  2. lib/main.dart is the entry point — the very first file that runs when your app starts, containing a main() function that kicks everything off.
  3. pubspec.yaml is your project's configuration file — dependencies (packages you're using), app metadata, and asset declarations all live here. Demo 2 below breaks down a real one.
  4. android/ and ios/ hold the actual native project shells Flutter builds into — you'll rarely touch these directly, but they're what turns your Dart code into a real .apk or .ipa file.
  5. assets/ is a folder you create and name yourself, for images, fonts, and other files your app needs — it has to be declared in pubspec.yaml before Flutter will actually bundle it in.
  6. test/ holds automated tests for your app — separate from your real app code, but structured to mirror it.
  7. build/ is entirely generated output — compiled files Flutter produces when you run or build your app. It's never edited by hand, and typically excluded from version control entirely.

PART 03Your First Widgets StatelessWidget, StatefulWidget, and the four or five widgets that show up in almost every screen you'll ever build.
🧩 Before you dive in — the two kinds of widget
Every widget you'll write is one of exactly two kinds — knowing which one you need is the very first decision in building any screen.
  1. StatelessWidget — a widget with no memory of its own. Give it the same inputs twice, get the exact same output twice. Perfect for anything that doesn't change once it's drawn — a label, an icon, a static card.
  2. StatefulWidget — a widget that can change over time, in response to user interaction or data arriving. It has an attached piece of memory (its "state") that persists across rebuilds.
  3. Every widget class has a build() method — this is the function Flutter calls to ask "what should you look like right now?" It returns a tree of other widgets, and Flutter calls it again anytime something changes.
  4. Text('...') displays a string. Icon(...) displays a built-in icon. Container(...) is a flexible box — color, padding, margin, size, decoration all live here.
  5. Every widget is a Dart class — this is Part 01's class lesson made concrete. Creating a widget on screen is exactly like Demo 3's Person('Amara', 25), just with a widget class instead.

StatelessWidget vs. StatefulWidget — the same button, both ways

Watch what happens when you tap each button. One of these classes literally cannot remember anything happened.

// StatelessWidget — no memory. Every tap does nothing to what's on screen.
class GreetingButton extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return ElevatedButton(onPressed: () {}, child: Text('Tap me'));
  }
}

// StatefulWidget — has memory, via setState (Part 05 covers this fully)
class CounterButton extends StatefulWidget {
  @override
  State createState() => _CounterButtonState();
}
class _CounterButtonState extends State {
  int taps = 0;
  @override
  Widget build(BuildContext context) {
    return ElevatedButton(
      onPressed: () => setState(() => taps++),
      child: Text('Tapped $taps times'),
    );
  }
}
This is the single most important distinction in Flutter

Neither is "better" — a static label should be a StatelessWidget, because giving it memory it doesn't need is wasted complexity. Anything that changes in response to interaction needs to be a StatefulWidget. Part 05 goes all the way into how setState actually works.

Four button types — and when to use each

Flutter ships several button widgets, each signaling a different importance level to the user.

PART 04Layout Widgets Row, Column, Stack, and the sizing widgets that control them — every playground below is a live HTML flexbox mockup built to move exactly like the real thing.
🧩 Before you dive in — main axis vs. cross axis
One idea underlies almost everything in this part — get this straight and every alignment property below makes sense on sight.
  1. Row arranges children left to right. Column arranges children top to bottom. Same concept, opposite direction.
  2. Every Row/Column has a main axis — the direction it lays children out in — and a cross axis, perpendicular to it. For a Row, main axis is horizontal, cross axis is vertical. For a Column, it's flipped.
  3. mainAxisAlignment controls spacing along the main axis — bunched at the start, spread evenly, centered, etc. crossAxisAlignment controls alignment across the cross axis.
  4. Expanded tells a child "take up all the leftover space." Flexible is similar but allows the child to be smaller than the space it's offered — Demo 2 makes the difference visible.
  5. Stack is different from Row/Column entirely — instead of arranging children in a line, it layers them on top of each other, like layers in a design tool. Positioned pins a Stack child to a specific spot.
  6. Padding adds space inside a widget's own edge. SizedBox is most often used as a fixed-size spacer between widgets, with no visible content of its own.

PART 05State Management Basics setState in full — and if Unlearn.js's state/render pattern is familiar, this is the exact same idea, wearing Flutter's syntax.
🧩 Before you dive in — what setState actually does
One method call, doing a very specific job — worth being precise about before Demo 1 uses it.
  1. State is just data that can change while the app runs — a counter's number, whether a checkbox is checked, a list of items. It lives inside a State class, attached to a StatefulWidget.
  2. setState(() { ... }) does two things: runs the code inside the parentheses (usually changing a variable), and tells Flutter "something changed, please call build() again."
  3. Changing a variable without calling setState updates the data, but Flutter never finds out — the screen simply won't update. This is the single most common beginner bug in Flutter.
  4. The widget lifecycle — initState() runs once, right when a StatefulWidget is first created (a good place to set up initial data). build() runs every time the screen needs to redraw. dispose() runs once, when the widget is removed for good (a good place to clean things up).
  5. "Lifting state up" means moving a piece of state from a child widget up to a shared parent, when two or more siblings both need access to it — Demo 2 below builds exactly this.
1

setState, live — and what forgetting it looks like

Both counters below use the same starting code. One calls setState, one doesn't. Tap both a few times.

class _CounterState extends State {
  int count = 0;

  void increment() {
    count++;              // ❌ the number DID change...
    // setState(() {});   // ...but Flutter was never told to redraw
  }

  void incrementCorrectly() {
    setState(() {
      count++;             // ✅ changes the data AND tells Flutter to redraw
    });
  }
}
The data changed both times — only the screen tells the difference

This is worth sitting with: the "broken" version's count variable really is incrementing under the hood, every single tap. The bug isn't in the math — it's that Flutter was never told to look again and redraw. This is exactly why setState exists as a distinct step from just changing a variable.

Lifting state up — two widgets, one shared source of truth

A counter display and a reset button are separate widgets — but they both need to agree on the same number. The count lives in their shared parent.

  State createState() => _ParentScreenState();
}
class _ParentScreenState extends State {
  int sharedCount = 0;   // lives in the PARENT, not in either child

  @override

    return Column(children: [
      CounterDisplay(count: sharedCount),                              // just displays it
      IncrementButton(onPressed: () => setState(() => sharedCount++)), // just requests a change
    ]);
  }
}

    PART 06Navigation & Screens Moving between screens, passing data along the way, and the bottom nav bar pattern nearly every app uses.
    🧩 Before you dive in — how screens actually work in Flutter
    There's no separate "router" file the way some web frameworks have — navigation is just another widget operation.
    1. A "screen" in Flutter is just a widget — usually a full-page one, but structurally no different from any other widget you've already seen.
    2. Navigator.push(context, route) puts a new screen on top of a stack, like adding a card to a deck — the old screen is still there underneath, just hidden.
    3. Navigator.pop(context) removes the current screen, revealing whatever was underneath — this is what a back button does.
    4. MaterialPageRoute is the most common way to describe "what screen to push" — it wraps the destination widget and handles the transition animation for you.
    5. Data can be passed forward as constructor arguments to the new screen, and passed back as a return value from Navigator.pop(context, someValue).

// on the detail screen, a back button:

    PART 07UI/UX Design Principles The difference between an app that works and one that feels genuinely well-made — spacing, contrast, touch targets, and typography, with real calculators, not just advice.
    🧩 Before you dive in — the vocabulary of "good design"
    These apply to every UI framework, not just Flutter — but Flutter gives you the exact tools to follow them.
    1. Material Design is Google's design system, built into Flutter by default — consistent spacing, elevation, and component styles. Cupertino is Flutter's iOS-styled widget set, for when you want an app to feel native to iOS specifically.
    2. The 8-point grid is a spacing convention: every margin, padding, and gap is a multiple of 8 pixels (8, 16, 24, 32...). It's arbitrary as a specific number, but consistency is what actually matters — it's why well-designed apps feel "aligned" even when you can't say exactly why.
    3. Touch target size — Apple and Google both recommend interactive elements be at least 44×44 (iOS) or 48×48 (Android) logical pixels, even if the visible icon inside is smaller — Demo 2 below shows why.
    4. Contrast ratio is a mathematical measure of how different two colors are — WCAG accessibility guidelines require at least 4.5:1 for normal text to be legible for people with low vision. It's a real formula, not a vibe — Demo 3 calculates it live.
    5. A type scale is a small, fixed set of font sizes used consistently across an app (rather than picking a new size every time), so text hierarchy feels intentional instead of random.

    PART 08Theming & Styling ThemeData, consistent color, and dark mode — the difference between hardcoding a color 200 times and defining it once.
    🧩 Before you dive in — why theming is a Part on its own
    Two ideas — one about where colors live, one about how they change.
    1. ThemeData is a single object where you define your app's colors, fonts, and component styles once, at the top level — every widget can then read from it instead of hardcoding its own values.
    2. Theme.of(context).colorScheme.primary is how a widget reads the current theme's primary color, rather than writing Colors.blue directly — this one line is what makes Demo 1 below possible.
    3. Dark mode, done properly, is just swapping which ThemeData is active — if every widget reads from the theme instead of hardcoding colors, the entire app switches appearance with zero changes to individual widgets.

    The mental model, named

    Widget tree in, pixels out — that's the whole engine

    Every part above was really building toward one idea: Flutter has exactly one job — take a tree of widget objects describing "what should be on screen," and turn it into pixels. Everything else is a consequence of that one job.

    • Why everything is a widget, even spacing. If the rendering engine's whole job is "read a tree and paint it," then padding, alignment, and color all have to be nodes in that same tree — there's no separate system for them to live in.
    • Why StatefulWidget and setState exist as a pair. The tree Flutter paints from is normally treated as fixed data — setState is the one sanctioned way to say "the data changed, please read the tree again and repaint."
    • Why the file structure separates lib/ from android/ and ios/. Your widget tree (in lib/) is platform-agnostic by design — the platform folders are just the native shells that let Flutter's own engine run on each one.
    • Why UI/UX principles matter even more here than on the web. Nothing about spacing, contrast, or touch targets is inherited "for free" from the browser or the OS the way it partially is on the web — you're deciding every pixel yourself, which means you're also responsible for every pixel being right.
    • Why theming exists as its own layer. If a color is hardcoded three times, dark mode means finding it three times. If it's read from one ThemeData object, the whole app changes by changing one thing — the same "one source of truth" idea from Unlearn.js's state pattern, applied to visual design instead of app logic.

    Once "widget tree in, pixels out" is automatic, reading unfamiliar Flutter code gets much faster — the real question is always just "what tree does this build, and what part of it changes over time."
