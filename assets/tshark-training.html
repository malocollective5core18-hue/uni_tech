02

Capture filters vs. display filters

This is the single most common junior mix-up, and it breaks captures in the field. Get it straight once and it never trips you up again.

Capture filter -fDisplay filter -Y
SyntaxBPF — same language as tcpdumpWireshark's own filter language
AppliedWhile capturing — non-matching packets are never savedAfter capture — hides/shows, nothing is discarded
Can undo?No — dropped packets are gone foreverYes — change the filter any time, all packets are still there
Exampletcp port 443tcp.port==443
Rule of thumb for juniors

If you're not 100% sure what you'll need yet, capture everything with no -f, save it with -w, then use -Y as many times as you want on the saved file. You can always narrow a display filter later — you can never get back what a capture filter threw away.

BPF capture filter cheatsheet

host 192.168.1.10          # to/from this host
src host 192.168.1.10      # FROM this host only
dst host 192.168.1.10      # TO this host only
net 192.168.1.0/24         # entire subnet
port 443                   # either direction
src port 53
dst port 22
portrange 8000-8080
tcp / udp / icmp / arp
ether host aa:bb:cc:dd:ee:ff
vlan 100

# combine with and / or / not
host 10.0.0.5 and port 443
tcp and not port 22
(host 10.0.0.1 or host 10.0.0.2) and tcp port 80

Ready-made combos you'll actually use

# web traffic only
tshark -i eth0 -f "tcp port 80 or tcp port 443"

# everything EXCEPT your own SSH session
tshark -i eth0 -f "not port 22"

# basic connectivity troubleshooting
tshark -i eth0 -f "icmp or arp"

# capture + save, filtered live
tshark -i eth0 -f "host 10.0.0.5" -w host5.pcap

06

Follow a stream

The "aha" moment for most juniors: TShark can reassemble an entire TCP conversation back into readable order — this is how you actually read what was sent, not just that something was sent.

Reconstruct stream #0 as ASCII

tshark -r cap.pcap -q -z follow,tcp,ascii,0
output will appear here
Why juniors care about this specifically

Notice the Authorization: Basic ... header — that's a base64-encoded (not encrypted) username and password, sent in the clear. Finding this exact pattern with -Y "http.authorization" then confirming it with follow,tcp,ascii is a real, common finding in cleartext-credential audits.

Find the stream number first

tshark -r cap.pcap -T fields -e tcp.stream -e ip.src -e ip.dst -e tcp.port | sort -u

Same idea, in hex

tshark -r cap.pcap -q -z follow,tcp,hex,0
# use hex when the payload is binary, not text (file transfers, TLS records)
07

Challenges

Score: 0 / 6

Same 30-packet capture from the Lab above. Each challenge is a real task — write the filter, submit it, get checked against the actual dataset. No answer key until you try.

1. Isolate all DNS traffic

Easy

Your teammate wants to see only the DNS queries and responses in this capture — nothing else.

Answer: dns

2. Pull every packet touching 198.51.100.7

Easy

That IP looks suspicious in the summary. Get every packet where it's either the source or the destination.

Answer: ip.addr==198.51.100.7

3. Isolate only real connection attempts (SYN, not SYN-ACK)

Medium

You need packets that are opening a connection — SYN set, ACK not set. SYN-ACK replies should be excluded.

Answer: tcp.flags.syn==1 and tcp.flags.ack==0

4. Find cleartext credentials

Medium

Security wants to know if any login happened over plain HTTP with credentials visible on the wire.

Answer: http.authorization

5. Find the failed DNS lookup

Medium

Somewhere in here a DNS query came back with an error code instead of an answer. Find it.

Answer: dns.flags.rcode!=0

6. Confirm the target rejected every scan attempt

Hard

Prove 10.0.0.14 responded to the scanning host with resets, not open ports. Filter to just the RSTs sent by 10.0.0.14.

Answer: ip.src==10.0.0.14 and tcp.flags.reset==1

Practical one-liners

# Top 10 talking IPs by packet count
tshark -r file.pcap -T fields -e ip.src | sort | uniq -c | sort -rn | head -10

# All unique DNS names queried
tshark -r file.pcap -Y "dns.flags.response==0" -T fields -e dns.qry.name | sort -u

# Every SYN packet = every connection attempt (spot a port scan)
tshark -r file.pcap -Y "tcp.flags.syn==1 and tcp.flags.ack==0" -T fields -e ip.src -e ip.dst -e tcp.dstport

# Retransmission rate over time (network health check)
tshark -r file.pcap -q -z io,stat,10,"tcp.analysis.retransmission"

# All HTTP User-Agent strings seen
tshark -r file.pcap -Y "http.request" -T fields -e http.user_agent | sort -u

# Live: print only DNS queries as they happen
tshark -i eth0 -Y "dns.flags.response==0" -T fields -e frame.time -e ip.src -e dns.qry.name -l

# Pull just SNI hostnames from encrypted TLS traffic
tshark -r file.pcap -Y "tls.handshake.extensions_server_name" -T fields -e ip.src -e tls.handshake.extensions_server_name

# Capture 60s on port 443, save, then summarize conversations
tshark -i eth0 -f "port 443" -a duration:60 -w tls60.pcap
tshark -r tls60.pcap -q -z conv,tcp

Suggested learning order for a brand-new junior

1tshark -D then -i <n> -c 20 — get comfortable capturing and reading raw output
2Capture filters (-f, BPF) — same syntax as tcpdump, a transferable skill
3Display filters (-Y) — this is 80% of real-world day-to-day usage
4-T fields -e ... — turns TShark into a scripting tool: pipe into awk, grep, CSV, Python/pandas
5-z conv,tcp / -z io,phs / -z http,tree — statistics turn a giant pcap into an instant summary
6follow,tcp,ascii — reconstructing a conversation is the "aha" moment for investigations
7--export-objects and TLS decryption — for real incident-response and forensics work
