CSS Blueprint

Every module below is a self-contained lab: pick values from the dropdowns, watch the live element change on the right, and read the exact CSS (and HTML) it produced underneath. Each one also lists what to do and what breaks things, straight from real production gotchas.

Margin · Lab 1/3

Uniform margin — one value, every side

A single margin value applies to all four sides equally. Margin pushes other elements away — it doesn't grow the target box itself, it grows the empty space around it. Watch both siblings move away from the target equally as you increase the value.

Margin · Lab 3/3
Special values — auto, negative, percentage

        
margin: auto on a block element with a set width centers it horizontally. A negative margin pulls the element (and can overlap a neighbor) instead of pushing it away. A percentage margin — on any side, including top/bottom — is always calculated from the container's width, never its height or the element's own size.

Do
    
          
  • Use margin: auto to horizontally center a block element that has an explicit width.
    • 
          
  • Reach for a negative margin deliberately, when you want one element to visually overlap a specific neighbor.
    • 
          
  • Remember vertical margins between block siblings collapse to the larger one — they don't add together.
    • 
        

        
Don't
    
          
  • Don't expect a percentage margin-top/margin-bottom to relate to the element's height — it's always a percentage of the container's width.
    • 
          
  • Don't use margin when you actually want to grow the box itself — that's padding's job, not margin's.

Unlike margin, it doesn't push siblings away — with the default box-sizing:content-box it makes the rendered box itself bigger. Padding · Lab 2/3
Per-side padding — four independent values

        
Same idea as margin's per-side controls, but padding pushes the content inside the box instead of the neighbors outside it. In a fixed-size box, growing one side's padding visibly shoves the centered content toward the opposite side.

Padding · Lab 3/3
Special values — percentage, em, and the aspect-ratio trick

        
A percentage padding — on every side, top/bottom included — is calculated from the container's width. An em padding scales with the element's own font-size. And the classic trick: a padding-bottom percentage on an empty box was the pre-aspect-ratio way to force a fixed width/height ratio (like 56.25% for 16:9 video embeds).

Do
    
          
  • Use box-sizing:border-box (see Module 01) so padding doesn't silently grow your declared width.
    • 
          
  • Use a percentage padding-bottom trick — or better, the modern aspect-ratio property — to keep embeds at a fixed ratio.
    • 
          
  • Use em padding when you want a component's spacing to scale automatically with its own text size.
    • 
        

        
Don't
    
          
  • Don't forget percentage padding on any side is relative to the container's width, including padding-top/padding-bottom — a very common surprise.
    • 
          
  • Don't add padding to shove content away from a border when what you actually want is space between this box and its neighbor — that's margin's job.

01
The Box Model

      
Every element is content → padding → border → margin, from the inside out. box-sizing decides whether width/height measure the content alone, or the content plus padding and border.


      

        

        

          

            
content box

            
Rendered size: —

          

        

      


      

        

        

      


      

        
Do
    
          
  • Set *{box-sizing:border-box} globally, once, project-wide.
    • 
          
  • Use border-box so a declared width stays the actual rendered width no matter what padding/border you add later.
    • 
          
  • Reach for negative margins deliberately to pull an element toward a neighbor.
    • 
        

        
Don't
    
          
  • Don't mix content-box math into a layout by accident — it's the #1 cause of "why is this 32px too wide."
    • 
          
  • Don't assume two stacked vertical margins add — block siblings collapse to the larger one, not the sum.
    • 
          
  • Don't forget margin collapsing stops inside flex/grid containers — items there never collapse margins.
    • 
        

      

    


    
    

      
02
Display Types

      
Before Flexbox/Grid, every element defaults to block, inline, or inline-block — this trio explains most "why won't this sit next to that" bugs.


      

        

        

          

            

              
Text flows in before the target and continues right after it, so you can see exactly how it behaves in a real sentence.

            

            
—

          

        

      


      

        

        

      


      

        
Do
    
          
  • Use inline-block (or better, flex/grid) when you need a row of boxes that still respect width/height/padding.
    • 
          
  • Use display:none to fully remove something from layout and the accessibility tree.
    • 
        

        
Don't
    
          
  • Don't set width/height on an inline element expecting it to apply — it's silently ignored.
    • 
          
  • Don't confuse display:none (removes layout space) with visibility:hidden (invisible but still occupies space).
    • 
          
  • Don't write inline-block elements across multiple HTML lines without noticing the "phantom whitespace" gap that appears between them.
    • 
        

      

    


    
    

      
03
Flexbox

      
Flexbox is a two-piece system: nothing below works until the parent has display:flex — every other property here is inert without it. Once that's set, parent properties (justify-* for the main axis, align-* for the cross axis) arrange all children at once, and a handful of child properties (flex-grow, align-self, order) let one item break away from the group. The labs below build up in that order: turn flex on, isolate the two axis properties, then layer in wrapping, sizing, and reordering.

Flexbox · Lab 5/6
flex-grow, flex-shrink & flex-basis — child sizing

        
These three control how one child's size compares to its siblings, independent of alignment. flex-basis is the starting size before growing/shrinking; flex-grow is how eagerly it claims leftover space; flex-shrink is how eagerly it gives space up when there isn't enough. Change child B's values and watch it claim (or give up) space relative to A and C, which stay at flex: 1 1 0.

Flexbox · Lab 6/6
order — visual reordering without touching the HTML

        
Every flex item defaults to order:0 and displays in source order. Give one item a different order value and it moves purely visually — screen readers and keyboard tab order still follow the original HTML, which is why order should only be used for cosmetic reshuffling, not to fix a real content-order problem.

Do
    
          
  • Set display:flex (or inline-flex) first — every other flex property is a no-op without it.
    • 
          
  • Use gap for spacing between flex items instead of margin hacks.
    • 
          
  • Use align-self on one item when everything else should follow align-items.
    • 
          
  • Remember align-items:stretch is the default — children with no set height already stretch to fill the cross axis.
    • 
        

        
Don't
    
          
  • Don't reach for align-content expecting it to do anything with flex-wrap:nowrap — it only affects multiple wrapped lines.
    • 
          
  • Don't confuse flex-basis:0% (equal columns, ignores content) with auto (content-weighted columns) — this is why flex:1 and flex:1 1 auto render differently.
    • 
          
  • Don't use order to fix content that's in the wrong place in the HTML — it only changes visual order, not reading or tab order.

  • Set display:grid first — every other grid property is a no-op without it.

  • Let two items share cells with overlapping grid-column/grid-row ranges — no position:relative or manual top/left math needed.

Box Shadow · Lab 6/6
Stacking shadows — the realistic "elevation" trick

        
box-shadow accepts a comma-separated list. Most design systems combine a tight, dark, low-blur shadow (contact shadow, close to the box) with a soft, wide, lighter one (ambient shadow, further out) instead of one big shadow — it reads as more realistic depth.

Do
    
          
  • Stack two shadows (tight dark one + soft wide one) for the realistic "elevation" look most design systems use.
    • 
          
  • Use filter:drop-shadow() instead when you need the shadow to follow a transparent PNG/SVG's actual shape.
    • 
          
  • Use a semi-transparent color (rgba()/hsla()) rather than solid black — real shadows blend with what's underneath.
    • 
        

        
Don't
    
          
  • Don't animate the blur/spread values directly on hover — it repaints and can jank. Animate a pre-shadowed pseudo-element's opacity instead.
    • 
          
  • Don't forget a negative spread is valid (shrinks the shadow smaller than the box) — negative blur is not.
    • 
          
  • Don't apply inset and expect the shadow to also show outside the box — it's one or the other per shadow layer, not both at once.

Overflow & Image Crop

      
Two labs here. First, text truncation — needs all three properties together: white-space:nowrap, overflow:hidden, text-overflow:ellipsis. Second, the classic <div class="box"><img></div> crop pattern used for every card thumbnail on the web.


      

        

        

          

            
This is a long line of sample text used to demonstrate overflow behavior inside a fixed-size box.

          

        

      


      

        

        

      


      
The .box > img crop pattern

      
The image is oversized on purpose — overflow:hidden on the parent .box clips it, and object-fit on the <img> controls how it fills that box.


      

        

        

          

            

              

            

          

        

      


      

        

          
          
        

        

        

      


      

        
Do
    
          
  • Use overflow:hidden on the .box parent to crop a child image to a fixed box, or to clip border-radius correctly.
    • 
          
  • Give the <img> width:100%; height:100%; object-fit:cover so it fills the box while keeping its aspect ratio, cropping any overflow.
    • 
          
  • Prefer display:flow-root over the old overflow:hidden float-containment hack — same effect, no accidental clipping.
    • 
        

        
Don't
    
          
  • Don't set text-overflow:ellipsis alone and expect it to work — without overflow:hidden + white-space:nowrap it silently does nothing.
    • 
          
  • Don't use object-fit:contain when you actually want a filled, cropped thumbnail — it letterboxes instead of cropping.
    • 
          
  • Don't wrap a dropdown/tooltip in a parent that has overflow:hidden — it will clip the dropdown even at z-index:9999.

text-align works on block containers; text-decoration is shorthand for line, color, style, and thickness.

Do
    
          
  • Set text-underline-offset on links so underlines don't collide with descenders like g, y, p.

Do

    •

Custom properties (CSS variables)

      
Defined once on :root, read anywhere with var(--name) — and unlike Sass variables, they're live in the browser and can even be changed from JavaScript.


      

        

        

          

            
Card using var(--space), var(--radius), var(--shadow)

          

        

      


      

        

        

      


      

        
Do
    
          
  • Reach for a class selector as your default — it's specific enough to override element defaults, without being as hard to override later as an ID.
    • 
          
  • Put shared values (spacing, radius, shadow, color) in :root custom properties instead of copy-pasting the same value across a stylesheet.
    • 
        

        
Don't
    
          
  • Don't reach for !important to "win" a specificity fight — it wins over everything, including future rules, and is hard to override again later except with another !important.
    • 
          
  • Don't style with IDs (#header) — high specificity makes them a pain to override from anywhere else, even a more sensible class rule.

13
Semantic Elements

      
Semantic tags (<header>, <nav>, <main>, <article>, <section>, <aside>, <footer>) look identical to <div>s visually — the difference is entirely in the accessibility tree. Switch the toggle to see what a screen reader gets either way.


      

        

        

          

            

              

            

          

        

      


      

        

        

      


      


      

        
Do
    
          
  • Use exactly one <main> per page — it's the skip-to-content target for assistive tech.
    • 
          
  • Give a <section> a heading (<h2>+) to be meaningful; otherwise it's often better as a plain <div>.
    • 
          
  • Add aria-label when the visual design has no visible label a screen reader could use — e.g. multiple <nav> elements.
    • 
        

        
Don't
    
          
  • Don't wrap everything in <div>s purely out of habit — you lose landmark navigation for free, for zero visual cost to switch.
    • 
          
  • Don't use <article> for something that only makes sense inside its page (use it for content that could stand alone if republished, like a blog post or comment).

Position — static, relative, absolute, fixed, sticky

      
position decides what an element's top/right/bottom/left offsets are measured from. static ignores them entirely. relative shifts the element from its own normal spot but leaves a hole behind. absolute jumps out of the flow and measures from its nearest ancestor that isn't static (falling back to the page). fixed does the same thing but always measures from the browser viewport, so it stays put even while you scroll. A real layout that needs it: badge + caption over a photo

      
This is the pattern behind almost every "sale" ribbon or image caption on the web: the card gets position:relative (so it becomes the "nearest positioned ancestor"), and the badge/caption get position:absolute so they lock to its corners instead of the whole page.


      

        

        

          

            

              

                
                -20%
                Caption pinned to the photo
              

            

          

        

      


      

        

        

      


      

        
Do
    
          
  • Pair position:absolute children with a position:relative (or sticky/fixed) parent on purpose — that parent becomes the "containing block" the offsets are measured from.
    • 
          
  • Use position:sticky + a top value for section headers or table headers that should stick once they hit the top of their scroll area, then release when their parent scrolls away.
    • 
          
  • Reach for relative with no offsets just to create a positioning context for an absolute child, even if the relative element itself doesn't move.
    • 
        

        
Don't
    
          
  • Don't forget an unstyled ancestor chain means absolute falls all the way back to the <html> element — "why is my badge in the corner of the whole page" is almost always a missing position:relative on the parent.
    • 
          
  • Don't use fixed inside a parent that has a transform, filter, or will-change set — any of those quietly turn that parent into the fixed element's containing block, and it stops tracking the viewport.
    • 
          
  • Don't confuse relative with absolute — relative still reserves its original space in the layout (everything else stays put), absolute removes it from flow entirely (siblings collapse into the gap).
    •
