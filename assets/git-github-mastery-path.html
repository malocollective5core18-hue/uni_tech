Git & GitHub Mastery Path

Reference sheets teach recognition — "oh right, that's what git rebase does." This is a practical build path: real exercises, in order, that force recall — reaching for the right command correctly, under pressure, without looking it up.

Work through the phases in order — each one assumes the last is solid. Check off each exercise step as you actually do it in a real practice repo, not just read it.

What you'll have at the end: a real GitHub repository with a genuine, messy-then-cleaned commit history, direct experience resolving an actual merge conflict, and a checklist of production practices you've exercised — not just read about.

Phase 1

Local Basics — Commits & History

GoalInternalize that a commit is a snapshot, and that Git tracks changes over time, not just current file state.
CheckpointIf you delete notes.txt right now with rm notes.txt, is your data actually gone?▾
No — it's still in every commit before the deletion. This is the entire point of version control. You should be able to explain why in one sentence before moving on.
Common pitfallWriting vague commit messages ("fix", "update", "asdf") during practice because "it's just practice." Build the real habit now — a message like "Fix off-by-one error in pagination loop" is the actual skill; typing git commit -m correctly is not.
Phase 2

The Three Areas — Staging & Undoing

GoalStop thinking of Git as one step ("save") and start seeing the three distinct areas — working directory, staging area, commit history — because every undo command only makes sense once you know which area it operates on.
CheckpointWhat's the practical difference between git checkout -- file and git reset file?▾
Write the answer in your own words before checking the reference sheet — the short version: reset moves changes back toward working (doesn't delete them), checkout --/restore actually discards them.
Common pitfallConfusing reset (moves changes back toward working, doesn't delete them) with checkout --/restore (actually discards them). This confusion is exactly how people lose real work — practicing the distinction now, on throwaway files, is cheaper than learning it on a real project.
Phase 3

Branching & Merge Conflicts

GoalGet comfortable branching and get comfortable with a real merge conflict — most juniors panic the first time they see conflict markers because they've never deliberately caused one on purpose in a safe environment.
CheckpointWhy did this conflict happen — what specific condition causes Git to conflict instead of auto-merging?▾
Two branches changed the same lines of the same file. Changes to different files, or different lines of the same file, merge automatically without asking you.
Common pitfallPanicking and running git merge --abort the first time conflict markers appear, then avoiding branching altogether. Do this exercise until resolving a conflict feels boring, not scary — that's the actual skill being built here.
Phase 4

GitHub & Remotes

GoalUnderstand that GitHub is just one remote copy of your repository — not a fundamentally different tool — and get comfortable with the fetch/pull/push cycle.
CheckpointWhat's the actual difference between git fetch and git pull?▾
If your answer doesn't mention that pull = fetch + merge, re-read that section of your reference sheet before continuing.
Common pitfallTreating git push as "save to the cloud" without understanding it can fail (rejected, because the remote has commits you don't have locally). Deliberately trigger this once: commit locally, make a different commit on GitHub's web editor, then try to push. Read the rejection message carefully, then git pull first and push again.
Phase 5

The Feature Branch Workflow & Pull Requests

GoalPractice the actual workflow used at almost every real company — not just knowing the commands, but the sequence and reasoning behind them.
CheckpointIn step 11, why do we merge main into the feature branch, rather than the other way around?▾
So the merge commit — and the conflict resolution — lives on the feature branch where a teammate can still review it via the PR, rather than landing directly on main unreviewed.
Common pitfallResolving PR conflicts entirely through GitHub's web editor without ever practicing the local resolution — the web editor works for trivial conflicts, but real conflicts in application code need your actual editor and the ability to run the code locally to verify the fix.

CheckpointFor each of the four tools above, could you explain when to reach for it — not just what it does — in one sentence?▾
Stash → switch branches without committing unfinished work. Cherry-pick → move one specific commit without the whole branch. Interactive rebase → clean up commits before sharing them. Bisect → find which commit introduced a bug.
Common pitfallLearning rebase -i and immediately wanting to rewrite history on a branch other people have already pulled — never rebase commits that have been pushed and shared, only your own local, not-yet-shared work (this is exactly why Phase 5's conflict resolution used merge, not rebase, once a PR was already open).
Phase 7

Clean History & Team Conventions

GoalThe difference between code that works and code a team can work with — a repo where every commit and branch name tells a clear story is a real, practiced skill, not a nice-to-have.
CheckpointIf a new teammate cloned your practice repo right now with zero context, could they understand what it is and get it running from the README and commit history alone?▾
If not, that's the specific gap to close — not a rhetorical question. Go fix whichever part (README or commit history) falls short.
Common pitfallTreating clean history as something to fix "later" — it compounds the same way messy code does; the habit has to form during the small, low-stakes commits, not retrofitted onto a large history once it's already tangled.
Phase 8

Production Readiness

GoalEverything so far worked on a solo practice repo with no consequences. Production repositories add guardrails specifically because mistakes there have real cost — get familiar with the guardrails themselves, not just the commands.
CheckpointWhy is "require a PR before merging to main" a meaningfully different safety net than just personally deciding to always open PRs?▾
It's enforced by the platform regardless of a moment of forgetfulness, tiredness, or urgency — the entire point of guardrails is that they don't depend on remembering to use them.
Common pitfallTreating branch protection, hooks, and CI as "senior developer concerns" to learn later. They're cheap to set up on a practice repo now, and the muscle memory of "this is just part of how repos work" is worth building before you're on a real team where getting it wrong has real cost.
