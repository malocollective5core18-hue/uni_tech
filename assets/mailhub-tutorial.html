Building MailHub — one Django app that sends, reads, and displays your email

Two independent flows, one beginner-friendly project: outbound — your dashboard tells Django to send an email over SMTP — and inbound — Django checks your inbox on a timer over IMAP and turns new mail into in-app notifications. React is built once and served by Django, so your finished app has one URL, not separate frontend and backend addresses.

Read this first. This guide is intentionally a local practice project. You need Python 3, Node.js/npm, PostgreSQL, and a Gmail App Password. Copy one file at a time, run each command before moving on, and never paste an App Password or .env value into GitHub, chat, or a screenshot.
  • Paste your Gmail + App Password once, MailHub verifies it before saving
  • Compose and send email straight from the dashboard
  • Background job checks your inbox automatically, every couple minutes
  • New mail shows up as a live notification badge — no manual refresh needed
  • Open one address when finished: http://127.0.0.1:8000/
outbound and inbound never touch the same code path — traced in Part D & Part E
Before you write any code

MailHub logs into Gmail on your behalf using an App Password — a 16-character / 16-digit passcode Google generates specifically for one app, separate from your normal Google password, and revocable at any time. Step 7 — Open mailer/models.py — EmailAccount

mailer/models.py
from django.db import models
from django.contrib.auth.models import User

class EmailAccount(models.Model):
    owner = models.OneToOneField(User, on_delete=models.CASCADE, related_name='email_account')
    email_address = models.EmailField()
    encrypted_app_password = models.BinaryField()

    imap_host = models.CharField(max_length=100, default='imap.gmail.com')
    imap_port = models.IntegerField(default=993)
    smtp_host = models.CharField(max_length=100, default='smtp.gmail.com')
    smtp_port = models.IntegerField(default=587)

    is_verified = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.email_address
Why encrypted_app_password is BinaryField, not CharField

Fernet encryption (Step 8) produces raw encrypted bytes, not text — storing bytes in a CharField would force an awkward text encoding step for no benefit. BinaryField stores exactly what Fernet.encrypt() hands back, with no conversion in between to get subtly wrong.

What never appears in this model, on purpose: a plain-text password field. The raw App Password only ever exists in memory for the few milliseconds it takes to encrypt it (Step 8) — it's never written to disk unencrypted, not even briefly, not even in a field meant to be temporary.
SETUP

Step 8 — Create mailer/crypto.py (new file)

mailer/crypto.py
from cryptography.fernet import Fernet
from django.conf import settings

def _fernet():
    return Fernet(settings.FERNET_KEY.encode())

def encrypt_password(plain_text_password):
    return _fernet().encrypt(plain_text_password.encode())

def decrypt_password(encrypted_bytes):
    return _fernet().decrypt(bytes(encrypted_bytes)).decode()
Why this lives in its own file instead of inline in models.py or views.py

Every place that ever needs to store or read the App Password — Step 12's save endpoint, Step 15's send function, Step 18's inbox poller — imports these same two functions. If the encryption method ever changes, there's exactly one file to update, and no risk of one call site quietly using a different (weaker) approach than the others.

It's the plain-text password coming in from the React form (Step 24) — this serializer field exists purely to receive it. write_only guarantees it can never accidentally be serialized back out in an API response; the view (Step 12) reads it, encrypts it via crypto.py, and stores only the encrypted bytes on the actual model.

Part C — The Test-Connection Endpoint verify before you ever save
SETUP

Step 11 — Create mailer/connection_test.py (new file)

This is the backend for the "Test Connection" form shown at the top of this page. It logs into both SMTP and IMAP with the given credentials and reports exactly which one failed, if either did — never saving anything.

mailer/connection_test.py
import smtplib
import imaplib

def test_smtp(email_address, app_password, smtp_host, smtp_port):
    try:
        with smtplib.SMTP(smtp_host, smtp_port, timeout=6) as server:
            server.starttls()
            server.login(email_address, app_password)
        return True, None
    except smtplib.SMTPAuthenticationError:
        return False, 'SMTP login rejected — check the email address and App Password.'
    except Exception as exc:
        return False, f'Could not reach SMTP server: {exc}'

def test_imap(email_address, app_password, imap_host, imap_port):
    try:
        connection = imaplib.IMAP4_SSL(imap_host, imap_port, timeout=6)
        connection.login(email_address, app_password)
        connection.logout()
        return True, None
    except imaplib.IMAP4.error:
        return False, 'IMAP login rejected — is IMAP enabled in Gmail settings?'
    except Exception as exc:
        return False, f'Could not reach IMAP server: {exc}'

def test_connection(email_address, app_password, imap_host, imap_port, smtp_host, smtp_port):
    smtp_ok, smtp_error = test_smtp(email_address, app_password, smtp_host, smtp_port)
    imap_ok, imap_error = test_imap(email_address, app_password, imap_host, imap_port)
    return {
        'smtp_ok': smtp_ok, 'smtp_error': smtp_error,
        'imap_ok': imap_ok, 'imap_error': imap_error,
        'success': smtp_ok and imap_ok,
    }
Why SMTP and IMAP are tested separately instead of stopping at the first failure

They fail for different reasons — a wrong password breaks both, but IMAP specifically failing while SMTP succeeds almost always means Step 3 of the external setup (enabling IMAP in Gmail) was skipped. Reporting both independently turns a vague "connection failed" into a specific, actionable next step for whoever's staring at the form.

from django.middleware.csrf import get_token
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from .connection_test import test_connection
from .crypto import encrypt_password
from .models import EmailAccount
from .serializers import EmailAccountSerializer

@api_view(['GET'])
@permission_classes([])
def csrf_view(request):
    return Response({'csrfToken': get_token(request)})

@api_view(['POST'])
@permission_classes([IsAuthenticated])
def test_connection_view(request):
    data = request.data
    result = test_connection(
        data.get('email_address'), data.get('app_password'),
        data.get('imap_host', 'imap.gmail.com'), int(data.get('imap_port', 993)),
        data.get('smtp_host', 'smtp.gmail.com'), int(data.get('smtp_port', 587)),
    )
    return Response(result)

@api_view(['POST'])
@permission_classes([IsAuthenticated])
def connect_account_view(request):
    data = request.data
    result = test_connection(
        data.get('email_address'), data.get('app_password'),
        data.get('imap_host', 'imap.gmail.com'), int(data.get('imap_port', 993)),
        data.get('smtp_host', 'smtp.gmail.com'), int(data.get('smtp_port', 587)),
    )
    if not result['success']:
        return Response(result, status=400)

    account, _ = EmailAccount.objects.update_or_create(
        owner=request.user,
        defaults={
            'email_address': data.get('email_address'),
            'encrypted_app_password': encrypt_password(data.get('app_password')),
            'imap_host': data.get('imap_host', 'imap.gmail.com'),
            'imap_port': int(data.get('imap_port', 993)),
            'smtp_host': data.get('smtp_host', 'smtp.gmail.com'),
            'smtp_port': int(data.get('smtp_port', 587)),
            'is_verified': True,
        },
    )
    return Response(EmailAccountSerializer(account).data, status=201)
Why connect_account_view re-tests the connection instead of trusting a prior test_connection_view call

The two calls could be seconds or minutes apart, and network requests from the browser can be replayed, retried, or intercepted — the save endpoint has to be safe to call on its own, verifying for itself, rather than trusting that "the test must have passed already" based on what the client claims.

Why update_or_create keyed on owner, not a fresh row every time

EmailAccount is a OneToOneField to User (Step 7) — one connected account per user, by design. Re-testing and re-saving replaces the existing row rather than accumulating duplicates, which matters if someone generates a new App Password later and needs to update it.

def dashboard(request):

        raise Http404('Dashboard has not been built. Run npm run build in dashboard/.')

Step 15 — Create mailer/mailer_service.py (new file)

mailer/mailer_service.py
import smtplib
from email.mime.text import MIMEText
from django.utils import timezone
from .crypto import decrypt_password

def send_email(outgoing_email):
    account = outgoing_email.account
    app_password = decrypt_password(account.encrypted_app_password)

    message = MIMEText(outgoing_email.body)
    message['Subject'] = outgoing_email.subject
    message['From'] = account.email_address
    message['To'] = outgoing_email.to_address

    try:
        with smtplib.SMTP(account.smtp_host, account.smtp_port, timeout=10) as server:
            server.starttls()
            server.login(account.email_address, app_password)
            server.sendmail(account.email_address, [outgoing_email.to_address], message.as_string())

        outgoing_email.status = 'sent'
        outgoing_email.sent_at = timezone.now()
    except Exception as exc:
        outgoing_email.status = 'failed'
        outgoing_email.error_message = str(exc)

    outgoing_email.save()
    return outgoing_email
Why the except clause updates and saves the row instead of letting the exception propagate

Same defensive boundary as every earlier project's "the core save must survive an external failure" rule. A bad send shouldn't crash the view calling this function — it should land as a status='failed' row with a readable error_message, which the dashboard can display, rather than a raw 500 error the user can't act on.

Step 18 — Create mailer/inbox_poller.py (new file)

mailer/inbox_poller.py
import imaplib
import email as email_lib
from email.utils import parsedate_to_datetime
from django.utils import timezone
from .crypto import decrypt_password
from .models import EmailAccount, IncomingEmail
from .notifications import notify

def poll_inbox(account: EmailAccount):
    app_password = decrypt_password(account.encrypted_app_password)

    connection = imaplib.IMAP4_SSL(account.imap_host, account.imap_port, timeout=10)
    connection.login(account.email_address, app_password)
    connection.select('INBOX')

    status, message_numbers = connection.search(None, 'UNSEEN')
    new_count = 0

    for number in message_numbers[0].split():
        status, raw_data = connection.fetch(number, '(RFC822)')
        parsed = email_lib.message_from_bytes(raw_data[0][1])

        message_id = parsed.get('Message-ID', f'no-id-{number.decode()}')
        if IncomingEmail.objects.filter(message_id=message_id).exists():
            continue

        received = parsedate_to_datetime(parsed.get('Date')) if parsed.get('Date') else timezone.now()

        incoming = IncomingEmail.objects.create(
            account=account,
            from_address=parsed.get('From', 'unknown'),
            subject=parsed.get('Subject', '(no subject)'),
            body=_extract_body(parsed),
            message_id=message_id,
            received_at=received,
        )
        notify(account.owner, 'received', f'New email from {incoming.from_address}: {incoming.subject}')
        new_count += 1

    connection.logout()
    return new_count

def _extract_body(parsed_message):
    if parsed_message.is_multipart():
        for part in parsed_message.walk():
            if part.get_content_type() == 'text/plain':
                return part.get_payload(decode=True).decode(errors='replace')
        return ''
    return parsed_message.get_payload(decode=True).decode(errors='replace')
Why the loop checks IncomingEmail.objects.filter(message_id=...).exists() before saving

IMAP's UNSEEN search reflects Gmail's own read/unread flag — but this poller never marks anything as read on Gmail's side, so the same unread emails would appear in every single poll if this check weren't here. The uniqueness check from Step 17 is what actually makes this function safe to call every two minutes forever.

Why _extract_body only looks for text/plain

Most emails are sent as multipart with both an HTML and a plain-text version bundled together. Grabbing the plain-text part keeps stored bodies simple and safe to display directly in the dashboard, without needing to sanitize arbitrary HTML from strangers' emails first — that sanitization is a real problem worth solving deliberately later, not accidentally skipped now.

from apscheduler.schedulers.background import BackgroundScheduler
from .models import EmailAccount
from .inbox_poller import poll_inbox

def poll_all_inboxes():
    for account in EmailAccount.objects.filter(is_verified=True):
        try:
            poll_inbox(account)
        except Exception as exc:
            print(f'Inbox poll failed for {account.email_address}: {exc}')

def start_scheduler():
    scheduler = BackgroundScheduler()
    scheduler.add_job(poll_all_inboxes, 'interval', minutes=2, id='poll_inboxes')
    scheduler.start()
    return scheduler
mailer/apps.py
import os
from django.apps import AppConfig

class MailerConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'mailer'

    def ready(self):
        if os.environ.get('RUN_MAIN') == 'true':
            from .scheduler import start_scheduler
            start_scheduler()
Why poll_all_inboxes swallows exceptions per-account instead of letting one failure stop the loop

One user's Gmail being temporarily unreachable, or their App Password having been revoked, shouldn't stop every other connected user's inbox from being checked in the same scheduled run — the same "one failure shouldn't take down an unrelated feature" boundary as the outbound send path.

Why the RUN_MAIN check, specifically

Django's development server (runserver) actually starts your app twice — once to watch for file changes (the auto-reloader) and once to actually serve requests. Without this check, the scheduler would start twice too, and the inbox would get polled every minute instead of every two, doubling every notification. RUN_MAIN is an environment variable Django itself sets only in the real server process, not the reloader-watcher one.

import { useState } from 'react';
import api, { primeCsrf } from '../api';

export default function ConnectEmailForm({ onConnected }) {
    const [form, setForm] = useState({
        email_address: '', app_password: '',
        imap_host: 'imap.gmail.com', imap_port: 993,
        smtp_host: 'smtp.gmail.com', smtp_port: 587,
    });
    const [status, setStatus] = useState(null);   // null | 'testing' | 'ok' | 'error'
    const [errorDetail, setErrorDetail] = useState('');

    const handleChange = (e) => setForm({ ...form, [e.target.name]: e.target.value });

    const handleTest = async () => {
        setStatus('testing');
        try {
            await primeCsrf();
            const response = await api.post('connect-account/', form);
            setStatus('ok');
            onConnected(response.data);
        } catch (err) {
            setStatus('error');
            const data = err.response?.data;
            setErrorDetail(data ? (data.smtp_error || data.imap_error || 'Connection failed.') : 'Network error.');
        }
    };

    return (
        <div className="connect-form">
            <input name="email_address" placeholder="you@gmail.com" onChange={handleChange} />
            <input name="app_password" type="password" placeholder="App Password" onChange={handleChange} />
            <button onClick={handleTest} disabled={status === 'testing'}>
                {status === 'testing' ? 'Testing...' : 'Connect Account'}
            </button>
            {status === 'ok' && <p className="ok">Connected successfully.</p>}
            {status === 'error' && <p className="error">{errorDetail}</p>}
        </div>
    );
}
Why this calls connect-account/ directly instead of test-connection/ first

Step 12's connect_account_view already re-tests before saving — calling test-connection/ first and then connect-account/ again would just test the same credentials twice for no benefit. One call, one round trip, same guarantee.

Step 25 — Create src/components/Dashboard.jsx

dashboard/src/components/Dashboard.jsx
import { useState, useEffect } from 'react';
import api, { primeCsrf } from '../api';

export default function Dashboard() {
    const [notifications, setNotifications] = useState([]);
    const [inbox, setInbox] = useState([]);
    const [composeTo, setComposeTo] = useState('');
    const [composeSubject, setComposeSubject] = useState('');
    const [composeBody, setComposeBody] = useState('');
    const [sending, setSending] = useState(false);

    useEffect(() => {
        const loadAll = () => {
            api.get('notifications/').then(res => setNotifications(res.data));
            api.get('inbox/').then(res => setInbox(res.data));
        };
        primeCsrf();
        loadAll();
        const interval = setInterval(loadAll, 15000);   // poll every 15s
        return () => clearInterval(interval);
    }, []);

    const handleSend = async () => {
        setSending(true);
        await api.post('send-email/', { to_address: composeTo, subject: composeSubject, body: composeBody });
        setComposeTo(''); setComposeSubject(''); setComposeBody('');
        setSending(false);
    };

    return (
        <div className="dashboard">
            <header>
                <h1>MailHub</h1>
                <span className="badge">🔔 {notifications.length}</span>
            </header>

            <section className="compose">
                <h2>Compose</h2>
                <input placeholder="To" value={composeTo} onChange={e => setComposeTo(e.target.value)} />
                <input placeholder="Subject" value={composeSubject} onChange={e => setComposeSubject(e.target.value)} />
                <textarea placeholder="Body" value={composeBody} onChange={e => setComposeBody(e.target.value)} />
                <button onClick={handleSend} disabled={sending}>{sending ? 'Sending...' : 'Send'}</button>
            </section>

            <section className="inbox">
                <h2>Inbox</h2>
                <ul>
                    {inbox.map(email => (
                        <li key={email.id}><strong>{email.from_address}</strong> — {email.subject}</li>
                    ))}
                </ul>
            </section>
        </div>
    );
}
Why setInterval polling instead of a WebSocket, for notifications this time

ChatSpace needed Channels because a chat message has to arrive within a second to feel real. A new-email notification arriving within 15 seconds of the 2-minute background poll (Step 19) is functionally instant by comparison — reaching for WebSocket infrastructure here would solve a responsiveness problem this app doesn't actually have. Simple polling is the right-sized tool for this specific latency requirement, not a lesser one.

Step 27 — Test the full flow

  1. Log into http://127.0.0.1:8000/admin/ first. The dashboard uses that Django session to authorize API requests.
  2. Open http://127.0.0.1:8000/, then use the Connect Account form with your real Gmail address and the App Password from the external setup panel.
  3. Compose and send a test email to yourself. Check OutgoingEmail in /admin/ — status should flip to sent, and the actual email should land in your inbox within seconds.
  4. Wait up to 2 minutes (the scheduler's interval from Step 19), then refresh the dashboard — the email should appear in the Inbox list, and the notification badge count should increase.

If the connection test keeps failing

Read the specific error first: Step 11 separates SMTP and IMAP failures on purpose. Then confirm: 2-Step Verification is enabled; you used a freshly generated 16-character App Password rather than your normal Gmail password; and you pasted it fully (spaces are okay, but no missing characters). Closing thesis

The pattern worth remembering

Outbound and inbound feel like one feature — "email" — but they're triggered by opposite things, and that difference shapes almost every file in this project.

Outbound is request-driven

A person clicks Send. Django runs, does the work, and returns a result in the same request/response cycle every other view in this series has used — nothing new architecturally, just SMTP instead of a database write.

Inbound is time-driven

Nobody clicks anything to make new mail arrive. Something has to run without a request triggering it — that's the entire reason APScheduler exists in this project, and it's a genuinely different shape of problem than any view function solves.

Every credential-handling decision in Part B and C — encrypting before storage, re-verifying before saving, never returning the password in an API response — exists because this project asks a user to hand over real account access. That deserves more care than a username and a throwaway password ever did in the earlier projects in this series, and the extra files here are what that care actually looks like in code.
