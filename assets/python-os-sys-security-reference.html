Python File Handling & Manipulation

Reading, writing, path handling with pathlib, structured formats, and the mistakes worth avoiding.

Opening and reading files

TaskCodeLinux Equivalent
Open and read whole filewith open('file.txt') as f: content = f.read()cat file.txt
Read line by linewith open('file.txt') as f: for line in f: print(line)while read -r line; do echo "$line"; done < file.txt
Read all lines into a listwith open('file.txt') as f: lines = f.readlines()mapfile -t lines < file.txt
Read first N lineswith open('file.txt') as f: [next(f) for _ in range(5)]head -n 5 file.txt
Read last N lineslines[-5:] (after reading all lines)tail -n 5 file.txt

Why with open(...) as f: instead of f = open(...): the with block (a context manager) guarantees the file is closed automatically, even if an exception happens partway through — the same discipline as always cleaning up a resource you opened, without having to remember a matching f.close() on every code path.

File modes cheat sheet

'r'

Read (default) — file must exist

'w'

Write — creates the file, overwrites if it exists

'a'

Append — creates the file if missing, adds to the end if it exists

'x'

Exclusive create — fails if the file already exists (safe "don't overwrite" mode)

'b'

Binary mode — combine with the above, e.g. 'rb', 'wb'

'+'

Read and write together, e.g. 'r+'

Common mistakes to avoid

  • Not using with — leaves file handles open, which can exhaust the OS's file descriptor limit under load, and risks losing unflushed writes if the program crashes.
  • Using string concatenation for paths ('folder' + '/' + 'file.txt') instead of Path('folder') / 'file.txt' or os.path.join() — breaks on Windows and is easy to get wrong with slashes.
  • Reading a huge file with .read() — loads the entire file into memory at once; for large files, iterate line by line instead (for line in f:), which reads lazily.
  • Forgetting binary mode for non-text files — opening an image or executable in text mode ('r') corrupts it; always use 'rb'/'wb' for anything that isn't plain text.

Why subprocess.run() is preferred over os.system() in real code: os.system() just hands a string to the shell — this makes it easy to accidentally build a command from untrusted input and get shell injection (someone passing ; rm -rf / as part of a filename, for instance). subprocess.run(['ls', '-la']) passes arguments as a list, never invoking a shell to interpret them, which is both safer and gives you the command's actual output/exit code back in Python instead of just seeing it printed.
python
import subprocess
result = subprocess.run(['ls', '-la'], capture_output=True, text=True)
print(result.stdout)
print(result.returncode)

Reading command-line arguments (sys.argv)

python
import sys

if len(sys.argv) < 2:
    print("Usage: python script.py <filename>")
    sys.exit(1)

filename = sys.argv[1]
print(f"Processing {filename}")

Run as: python script.py report.txt → sys.argv is ['script.py', 'report.txt'].

Why sys.exit(1) and not just letting the script end normally: exit codes are how shell scripts and CI pipelines detect success/failure. 0 means success by convention; any nonzero value signals an error — command1 && command2 relies on this exact convention to decide whether to run command2 at all.

Reading piped input

python
import sys
for line in sys.stdin:
    print(line.strip().upper())

Run as: cat names.txt | python uppercase.py — this script behaves like a Linux filter command (tr, sort, grep), reading from stdin and writing to stdout, which is what lets it be chained with | into any pipeline.

Low-level sockets (what requests is built on top of)

python — minimal TCP client
import socket

# A minimal TCP client
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.connect(('example.com', 80))
sock.sendall(b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n')
response = sock.recv(4096)
print(response.decode())
sock.close()

This is, at a low level, exactly what curl example.com and requests.get('http://example.com') are doing underneath — opening a TCP connection, writing raw HTTP text, reading the raw response.

python — minimal TCP server
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(('0.0.0.0', 9000))
server.listen(1)
print("Listening on port 9000...")

conn, addr = server.accept()
print(f"Connection from {addr}")
data = conn.recv(1024)
conn.sendall(b'Echo: ' + data)
conn.close()

Test it with: nc localhost 9000 or curl telnet://localhost:9000 in another terminal — this is the same fundamental pattern a Django dev server or an Actix service is built on, just without a web framework wrapped around it.

Networking for Cybersecurity & Pentesting

Authorized use only.

⚠ Scope and ethics, stated plainly

Every technique below is standard defensive/offensive security education — the same material covered in any introductory security course, nmap's own documentation, or the Python socket module docs.

Use these only against systems you own, or have explicit written authorization to test (a home lab, a CTF platform, or a client engagement with a signed scope document).

Running these against systems you don't control is illegal in most places, regardless of intent — treat that as a hard boundary, not a suggestion.

A basic TCP port scanner

The classic "how port scanning actually works" example — useful for understanding what tools like nmap are doing, and for quick checks on your own infrastructure.

python
import socket

def scan_port(host, port, timeout=1):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(timeout)
    result = sock.connect_ex((host, port))   # returns 0 if the port is open
    sock.close()
    return result == 0

def scan_range(host, start_port, end_port):
    open_ports = []
    for port in range(start_port, end_port + 1):
        if scan_port(host, port):
            open_ports.append(port)
    return open_ports

if __name__ == '__main__':
    target = '127.0.0.1'          # only ever a host you own/control
    print(f"Scanning {target}...")
    for port in scan_range(target, 1, 1024):
        print(f"Port {port} is OPEN")
Why connect_ex instead of connect: connect() raises an exception on a closed/filtered port, which would require wrapping every check in try/except. connect_ex() returns an error code instead of raising — 0 specifically means the TCP handshake succeeded, i.e. the port is open — which makes scanning a range of ports a clean loop instead of a loop full of exception handling.
Why this is educational, not a replacement for nmap: a real scanner needs to handle timing, retries, service fingerprinting (what's actually running on an open port, not just that it's open), and evasion of intrusion detection — all of which nmap already does correctly and efficiently. Writing your own is for understanding the mechanism, not for actual engagement work.

Calling nmap from Python (the practical approach)

For real work, call the actual tool and parse its output rather than reimplementing it:

python
import subprocess
import json

def run_nmap_scan(target, ports='1-1024'):
    result = subprocess.run(
        ['nmap', '-p', ports, '-oX', '-', target],   # -oX - outputs XML to stdout
        capture_output=True, text=True
    )
    return result.stdout   # parse this XML with xml.etree.ElementTree for structured results

Again: subprocess.run with a list of arguments, not a shell string — same injection-avoidance reasoning as Section 02.

Checking your own TLS/SSL certificate expiry

A genuinely useful, purely defensive script — checking that a certificate on your own server isn't about to expire:

python
import ssl
import socket
from datetime import datetime

def check_cert_expiry(hostname, port=443):
    context = ssl.create_default_context()
    with socket.create_connection((hostname, port), timeout=5) as sock:
        with context.wrap_socket(sock, server_hostname=hostname) as ssock:
            cert = ssock.getpeercert()
            expires = datetime.strptime(cert['notAfter'], '%b %d %H:%M:%S %Y %Z')
            days_left = (expires - datetime.utcnow()).days
            print(f"{hostname} certificate expires in {days_left} days")

check_cert_expiry('example.com')

This is the kind of check worth running as a scheduled cron job against your own domains — a lapsed TLS certificate is one of the most common, entirely preventable production incidents.

The honest summary

Working through all six layers meaningfully reduces your attack surface and the blast radius of any single failure — that's what "defense in depth" actually buys you.

It does not, and cannot, guarantee "zero vulnerabilities": new vulnerabilities get discovered in dependencies you didn't write, and human error is never fully eliminated.

The realistic goal is a system where a single missed checkbox doesn't cascade into a full compromise, and where you find out about problems from your own monitoring before an attacker or a user does.
